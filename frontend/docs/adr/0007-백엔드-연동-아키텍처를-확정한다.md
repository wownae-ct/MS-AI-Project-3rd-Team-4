## 맥락

### 1. 백엔드가 인증을 재도입했고, 프론트 전제가 통째로 무효가 됐다

백엔드는 2026-08-24에 v4.0으로 올라가면서 **쿠키 세션 인증**을 도입했다. 프론트가 갖고 있던 전제(무인증 MVP · 23 REST · 시드된 단일 웨딩)는 전부 성립하지 않는다.

| 항목 | 프론트가 알고 있던 값 | 실측 |
|---|---|---|
| 인증 | 없음 | **쿠키 세션 `wr_session`** + 소셜 2종(구글·네이버) |
| 엔드포인트 | 23개 | **36개** (OpenAPI 노출 34 + OAuth 비노출 2) |
| 웨딩 데이터 | 시드된 단일 행 | **사용자 1명 = 웨딩 1개** (`owner_user_id UNIQUE`) |
| 카테고리 | 7개 | **9개** |
| 상담 응답 | 미확인 | **SSE 스트리밍** · 이벤트 **7종** |

**로그인·온보딩 없이 쓸 수 있는 데이터 API는 `GET /categories`와 `GET /vendor-cases` 둘뿐이다.** 나머지는 401 또는 404를 낸다.

### 2. 프론트에는 전송 계층이 한 줄도 없다

주제 전환(`f23d27a`) 때 `shared/api`·`shared/config`·`shared/lib`를 삭제했고 이후 복원하지 않았다. **`VITE_API_BASE`를 읽는 코드가 0건**이다(`src/vite-env.d.ts:23`의 타입 선언만 존재 — grep 실측). 즉 이 결정은 「기존 계층을 고치는」 것이 아니라 **처음부터 세우는** 것이고, 그래서 지금 형태를 정할 수 있다.

### 3. 화면 6개 중 2개만 구현됐고, 그 2개도 합성 데이터를 본다

S2 대시보드·S5 리포트가 `entities/wedding/model/sample-data.ts`를 읽는다. 나머지 4개(S1·S3·S4·S6)는 라우트·폭·셸 배선만 있는 스캐폴드다. **연동은 「새 화면을 만드는 일」과 「기존 화면을 갈아 끼우는 일」을 동시에 요구한다.**

### 4. 연동 대상은 로컬이지만, 설계 사정권은 배포까지다

작업은 WSL 로컬 백엔드(`http://localhost:8000`)에 붙여 진행한다. 그런데 로컬은 **문제를 해결하는 것이 아니라 가린다** — `localhost:5173`↔`localhost:8000`은 포트가 site 정의에 들어가지 않아 **same-site**이므로, 배포 시점에 되살아나는 제약(크로스 사이트 쿠키 · CSP · OAuth 리다이렉트 · SSE 프록시 타임아웃)이 로컬에서는 **한 건도 재현되지 않는다.**

> MDN Glossary · Site: *"These are considered the same site because **the port number is ignored when determining the site**"*

**화면을 다 만든 뒤에 이 제약을 만나면 전송 계층과 배포 토폴로지를 함께 바꿔야 한다.** 그래서 설계는 배포 시점의 제약을 지금 계약에 반영한다.

## 검토한 대안

### A. 연동 전략

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **A1. 인증 우선 수직 관통** | 매 단계가 브라우저에서 실제로 검증된다 — 로그인해야 데이터가 보이므로 **가짜 초록불이 구조적으로 안 나온다** | 화면 진도(S4·S6)가 잠시 멈춘다 · 개발에 백엔드 기동이 필요하다 | **채택** |
| A2. 계약 목(MSW) 우선 | 백엔드 기동 의존 0 · 화면 진도 유지 · 번들 무관(dev 전용) | 목이 계약을 잘못 반영하면 **마지막에 한꺼번에 터진다** | 기각 |
| A3. 어댑터 + 화면별 점진 전환 | 되돌리기 쉽고 병행 가능 | 전환 기간 내내 두 경로 공존 · 파생 필드(`dDay`·`shortLabel`) 때문에 어댑터가 두꺼워진다 | 기각 |

**A2를 기각한 사유가 이 저장소의 사고 이력이다.** 여기서 실제로 난 사고는 전부 **「중간 점검은 초록인데 끝단에서만 죽는」** 형태였다.

| 사고 | 중간 점검 | 실제 |
|---|---|---|
| `VITE_API_BASE`에 `http://` | `curl`은 308을 따라가 성공 | 브라우저에서만 `TypeError: Failed to fetch` |
| `SameSite=Lax` | CORS 프리플라이트 200 · `allow-credentials: true` | 로그인 후 모든 요청이 401 |
| `CODEOWNERS` | `codeowners/errors` 응답이 빈 배열 | 자동 리뷰 요청이 **한 번도 일어난 적 없음** |
| `imagePullPolicy: Always` | 파드 `1/1 Running` | 37커밋 뒤처진 이미지 |

**A2는 이 형태의 위험을 하나 더 만든다.** A1은 로그인이 성립해야 다음 화면이 보이므로 같은 실패가 구조적으로 불가능하다.

### B. 데이터 페칭

| 대안 | 번들 비용 (gzip) | 판정 |
|---|---|---|
| **B1. TanStack Router 내장 로더** | **0 B** — 기계가 이미 번들에 있다 | **채택** |
| B2. TanStack Query 도입 | **13,854 B** (bundlephobia 실측, v5.102.3) | 기각 |
| B3. 자체 캐시 스토어 구현 | 미상 (신규 코드) | 기각 — 라우터가 이미 하는 일을 다시 짓는다 |

**B1이 가능하다는 근거는 측정이다.** `dist/assets/index-*.js`를 grep한 결과 `staleTime` · `gcTime` · `loaderDeps` · `beforeLoad` · `invalidate` · `pendingComponent` · `shouldReload`가 **7개 중 7개 모두 이미 들어 있다.** 옵션을 쓰는 것은 새 코드를 들이지 않는다 — `defaultPreload: 'intent'`를 켠 커밋(`fa9373d`)이 **+8 B**였던 것과 같은 구조다. (`isRedirect`만 트리셰이킹으로 빠져 있어 소량 증가한다.)

**B2를 기각한 근거도 측정이다.** 현재 JS 합계 여유가 **1,371 B**인데 13,854 B는 그 **10.1배**다. 살 수 없고, B1이 성립하므로 살 이유도 없다.

### C. 지원 브라우저 범위

| 대안 | 크로스 사이트 쿠키 | 필요한 대응 | 판정 |
|---|---|---|---|
| **C1. Chromium 전용 (Chrome + Edge)** | 기본 허용 | `SameSite=None` 한 줄 | **채택** |
| C2. Safari/iOS 포함 | **전면 차단, 예외 없음** | Storage Access API 도입(사용자 제스처+프롬프트) **또는** same-site 토폴로지로 인프라 변경 | 기각 |
| C3. Firefox 포함 | 사이트별 분리 저장소 | 위와 동일 | 기각 |

공식 원문:

> WebKit · Tracking Prevention: *"**ITP by default blocks all third-party cookies.**"* · *"**There are no exceptions to this blocking.**"* · *"Third-party cookie access can only be granted through the **Storage Access API** and the temporary compatibility fix for popups."*
>
> MDN · Third-party cookies: *"Google Chrome doesn't block third-party cookies by default, **only in Incognito mode, or when users explicitly set it** to block third-party cookies"* · (Firefox) *"This gives third-party cookies **a separate cookie jar per site**, preventing cross-site tracking."*

**Edge를 넣는 것은 추가 비용이 0이다.** Edge의 추적 방지는 **분류 기반**이지 서드파티 전면 차단이 아니다.

> Microsoft Learn · Tracking prevention in Microsoft Edge: *"**Balanced (Default)** … Balanced aims to **block trackers from sites that users never engage with**."* · *"To classify online trackers … Microsoft Edge uses the disconnect.me website's open source **Tracker Protection lists**."*

우리 API 호스트는 어느 추적기 목록에도 없으므로 대조 자체에서 걸리지 않는다. Safari의 *"all … no exceptions"* 와 **성격이 근본적으로 다르다.**

단 하나의 예외가 있다 — Edge **Strict** 모드다.

> Microsoft Learn · Fix Microsoft Edge not saving cookies or sign-in sessions: *"**Strict tracking prevention can block third-party authentication cookies.**"*

기본값이 아니므로 대다수는 무관하고, D3의 행동 판별이 이 경우를 그대로 잡는다.

## 결정

**여섯 가지를 함께 결정한다.**

### D1. 슬라이스를 3개로 나누고, 계약 어휘는 `shared/api`에 둔다

| 슬라이스 | 담는 것 |
|---|---|
| `shared/api/` | 전송(`client.ts`) · 에러 정규화(`errors.ts`) · base URL 검증(`env.ts`) · **계약 어휘(`contract.ts`)** |
| `entities/session/` | `auth/*` 6개 · `AuthUserOut` · 세션 판정 |
| `entities/wedding/` | 웨딩 · 카테고리 · 예산/납부 · 체크리스트 · 타임라인 · 대시보드 · 리포트 · 벤치마크 · 개인화 · 업체사례 |
| `entities/chat/` | 상담 세션 · 메시지 · SSE 스트림 · 평가 |

**`entities/wedding`을 쪼개지 않는 것은 취향이 아니라 강제다.** `.oxlintrc.json`의 entities override가 `@/entities/**` 전체를 차단한다(원문: *"entities는 상위 레이어와 다른 entity 슬라이스를 import할 수 없다"*). 그런데 백엔드 응답이 도메인을 가로지른다.

- `DashboardSummaryOut` 하나가 `categories[]`(카테고리) + `upcoming_items[]`(타임라인·체크리스트 판별 유니온)를 함께 담는다
- `ReportOut`이 `payment.py`의 `UpcomingPaymentOut`을 재사용한다

→ 슬라이스를 나누면 **이 DTO들이 교차 import를 강제해 경계 위반이 된다.** `entities/wedding/model/types.ts` 머리말이 목업 기준으로 이미 논증해 둔 것과 같은 결론이 **백엔드 응답 모양으로도 확인됐다.**

Literal 유니온(`CategoryCode` 9 · `RegionCode` 17 · `SourceTier` 4 · `Verdict` 3 …)은 세 슬라이스가 전부 쓰므로 entities에 둘 수 없다. **`shared/api/contract.ts`에 둔다** — shared는 최하층이라 위에서 자유롭게 import되고, 깊은 경로 강제 규칙도 없다([layers.md](../architecture/layers.md)가 「shared 세그먼트 공개 API 강제」를 의도적으로 미도입으로 남겨 뒀다).

### D2. 데이터 페칭은 라우터 로더로 한다 — 라이브러리를 추가하지 않는다

읽기는 라우트 `loader` + `staleTime`/`gcTime`, 쓰기는 직접 호출 후 `router.invalidate()`. 인증 판정은 `beforeLoad` + `throw redirect()`.

**세 가지를 함께 정한다 — 라이브러리를 안 쓰기로 한 이상 라이브러리가 해 주던 일을 우리가 명시해야 한다.**

| 항목 | 결정 | 근거 |
|---|---|---|
| `staleTime` | **라우트마다 명시한다.** 기본값에 기대지 않는다 | 공식: *"The default staleTime is 0, **causing background reloads on every route match**."* |
| 취소 | 로더는 `abortController.signal`을 전송 계층에 넘긴다 | 공식이 명시한 사용법. 안 넘기면 빠르게 이동할 때 철 지난 응답이 새 화면을 덮어쓴다 |
| **세션 조회 캐시** | **`beforeLoad`에 캐시를 씌운다** | 아래 |

🚨 **`beforeLoad`는 캐시되지 않는다.** TanStack Router 내부 문서 원문:

> *"The beforeLoad context is **not a cache**. … **A subsequent navigation rebuilds merged context from the parent and reruns beforeLoad**, even when reusing completed loader data."*

즉 인증 가드를 `beforeLoad`에 두면 **탭을 옮길 때마다 `GET /auth/me` 왕복이 하나씩 붙는다.** 로컬에서는 안 보이고 배포에서만 드러나는 종류의 비용이다. 그래서 세션 조회에 TTL 캐시를 씌우고 가드는 그 캐시를 읽는다 — 상세 계약은 [backend-integration.md](../architecture/backend-integration.md) §3.7.

`loader`로 옮기는 것으로는 해결되지 않는다 — **리다이렉트 판정은 자식 로더가 돌기 전에 끝나야** 하므로 `beforeLoad`에 있어야 한다.

### D3. 지원 브라우저는 Chromium 계열(Chrome · Edge)로 한정한다

그리고 **미지원 환경을 조용히 실패시키지 않는다.** 판별은 UA가 아니라 **행동**으로 한다 — 로그인 200 직후 `GET /auth/me`가 401이면 쿠키가 왕복하지 못한 것이므로 안내를 띄운다. UA 판별은 **Chrome 시크릿 모드**(UA 동일)와 **Edge Strict**를 잡지 못한다.

### D4. 인증 우선 수직 관통 순서로 구현한다

전송 계층 → `/login` → `_authed` 가드 → S1 온보딩 → S2 실데이터 전환 → S4 → S6 → S3 → S5 전환.

### D5. 번들 예산을 3층으로 나눈다

> ⚠️ **용어 주의 — 여기서 「예산」은 돈이 아니라 JS 번들의 크기다.** 이 제품의 도메인에도 「예산」이 있어(웨딩 예산 · S4 예산 화면 · `BUDGET_EXCEEDED`) 같은 단어가 두 뜻으로 쓰인다. **이 절의 모든 수치는 gzip 압축 후 바이트**이고, 게이트 이름은 `check-bundle-budget.mjs`다. 도메인 쪽을 가리킬 때는 반드시 「웨딩 예산」으로 적는다.

| 층 | 한도 (gzip 바이트) | 성격 |
|---|---|---|
| **초기 청크** — 첫 방문에 무조건 받는 JS | **96,000 유지 (엄격)** | LCP 계약. 화면이 늘어도 움직이면 안 된다 — 움직였다면 lazy여야 할 것이 정적으로 샜다는 신호 |
| **화면별 lazy 청크** — 그 화면에 갈 때만 받는 JS | 화면당 상한 (신설) | 한 화면의 폭주를 잡는다 |
| **합계** — 모든 JS 청크의 합 | `초기 한도 + (lazy 화면 수 × 화면당 상한)` **규칙으로 산출** | 화면을 추가하면 자동으로 는다 |

**셋을 나누는 이유는 성격이 다르기 때문이다.** 초기 청크는 첫 방문 비용이라 LCP를 직접 좌우하고(폰트가 그 뒤로 밀린다), lazy 청크는 첫 방문 비용이 **아니다.** 지금 게이트는 둘을 같은 「합계」 한도에 섞어 세므로, 화면을 추가할 때마다 **초기 예산이 압박받는 것처럼 보인다.**

합계를 고정 숫자로 두면 화면을 추가할 때마다 숫자를 올리게 되고 그 숫자는 곧 근거를 잃는다. 이 저장소가 이미 쓰고 있는 원칙 — **빨리 썩는 값은 값이 아니라 세는 법을 적는다** — 을 번들 예산 게이트에 적용한다.

**화면당 상한의 구체값(= lazy 청크 하나가 넘으면 안 되는 gzip 바이트)은 이 ADR에서 정하지 않는다** — 근거가 될 수 있는 유일한 수치(S1의 43 kB)가 `inventory.md`의 **추정치이고 실측이 아니다.** S1 착수 시 Base UI 6종을 실제로 번들해 재고 그 값으로 정한다.

참고로 현재 lazy 청크 실측값은 이렇다 — `timeline`/`budget`/`onboarding`/`category` 각 **0.44~0.46 kB**(내용이 비어 있는 스캐폴드), `report` **1.49 kB**(구현됨), `style-guide` **14.50 kB**. 즉 **구현된 화면 하나가 스캐폴드의 3배 이상**이고, S1은 신규 Base UI 6종이 붙어 그보다 훨씬 크다.

### D6. `build.target`을 `["chrome126", "edge126"]`으로 올린다

**번들 이득 때문이 아니다 — 이득은 측정 결과 없다.**

| `build.target` | JS 합계 (gzip) | 최대 단일 | CSS (gzip) |
|---|---|---|---|
| `chrome111`,`edge111` (현행) | 110,629 | 92,874 | 4,387 |
| `chrome120`,`edge120` | 110,652 (**+23**) | 92,878 | 4,387 |
| `chrome126`,`edge126` | 110,637 (+8) | 92,874 | 4,367 (**−20**) |
| `chrome134`,`edge134` | 110,637 | 92,874 | 4,367 |
| `esnext` | 110,637 | 92,874 | 4,367 |

올리는 근거는 **조용한 실패 경로를 제거하는 것**이다. [toolchain.md](../architecture/toolchain.md)가 적어 둔 함정 — *"하한 초과 CSS 기능은 조용히 무시된다"* — 의 대상 3건(`@starting-style` 117 · `light-dark()` 123 · `anchor-*` 125)이 **전부 하한 안으로 들어온다.** 빌드도 린트도 잡지 않던 실패 경로가 사라진다.

`chrome126`을 고른 이유: CSS −20 B가 여기서 전부 나오고 134·esnext도 같은 값이다. **`esnext`를 쓰지 않는 이유**는 하한이 「빌드 시점의 최신」으로 떠다녀 재현성이 깨지기 때문이다 — `vite.config.ts`가 Vite 기본값(`baseline-widely-available`)을 거부한 사유(*"타깃이 암묵적으로 바뀌므로 위임하지 않는다"*)와 정확히 같은 문제다.

Chrome 안정 버전은 **151**이다(chromiumdash API + 브라우저 UA 양쪽 확인). 126은 그보다 25 버전 뒤라 실사용자 커버리지가 사실상 100%다.

#### 적용 후 규범 게이트의 선언 수가 줄었다 — 유령 신호가 아니다

적용하면 게이트 요약이 **`선언 404개(색 17)` → `선언 401개(색 16)`** 로 바뀐다. 이 저장소는 **설명되지 않는 선언 증감을 유령 신호로 취급**하므로 **두 타깃의 산출 CSS를 직접 비교해 원인을 확정했다.**

```css
/* chrome111 */  :root{--lightningcss-light:initial;--lightningcss-dark: ;color-scheme:light}
/* chrome126 */  :root{color-scheme:light}
```

lightningcss는 `color-scheme`을 만나면 `light-dark()`를 다운레벨하기 위한 **폴리필 스캐폴딩 커스텀 속성**을 깔아 둔다. 그런데 이 저장소는 **`light-dark()`를 한 번도 쓰지 않는다**(산출 CSS 실측: 양쪽 다 등장 0회). 즉 chrome111에서 그 두 선언은 **순수한 죽은 무게**였고, `light-dark()`가 네이티브인 126에서는 나오지 않는다.

**디자인 규범에는 영향이 없다** — 의도한 `color-scheme: light`는 그대로 남고, `prefers-color-scheme`은 **양쪽 다 0회**라 다크모드 금지(D 계열)가 유지된다. 색 **선언 자체는 15개로 동일**하다(줄어든 「색 17→16」은 게이트가 커스텀 속성 원자까지 세기 때문이다). 규범 검사 6종은 전부 통과한다.

**이것이 D6의 근거를 그대로 보여 준다** — 타깃 상향이 산 것은 바이트가 아니라 **「쓰지도 않는 기능의 폴리필이 조용히 깔려 있던 상태」의 해소**다.

## 결과

### 쉬워지는 것

- **배포 시점에 아키텍처를 뒤집을 위험이 사라진다.** C1 결정으로 Storage Access API도, same-site 토폴로지 변경(SWA Free는 `/api/*` 프록시 불가 · Linked Backend는 AKS 미지원)도 필요 없다. 백엔드 `samesite="none"` 한 줄이면 배포가 성립한다
- **번들 예산 논쟁이 줄어든다.** 초기 청크만 엄격히 지키면 되고, 화면 추가는 규칙이 흡수한다
- **미지원 브라우저가 드러난다.** 행동 판별이라 Chrome 시크릿 · Edge Strict · 사용자 설정 차단까지 같은 경로로 잡힌다

### 어려워지는 것

- **개발이 백엔드 기동에 묶인다.** 목 계층이 없으므로 로컬 백엔드가 떠 있어야 화면을 진행할 수 있다. 백엔드도 같은 담당이라 통제 가능하지만, 기동 절차가 개발 전제가 된다
- **`shared/api/contract.ts`의 드리프트 책임을 프론트가 진다.** 백엔드는 하루에 8커밋씩 움직인다. 대조 게이트를 함께 둔다 — 상세는 [api-contract.md](../architecture/api-contract.md)
- **Safari/iOS 사용자를 받지 못한다.** 이건 되돌림 비용이 가장 큰 항목이다(아래)

### 재검토로 남긴 것

**ADR 0005 §결정 3(「첫 화면만 정적 import」)의 전제가 바뀌었다.** 지금은 대시보드만 정적인데, D4로 **첫 화면이 `/login`이 된다.**

- 신규 사용자: `/login` → `/onboarding` → `/`
- 재방문 사용자(세션 30일): `/` 또는 `/onboarding`

둘 다 정적으로 넣으면 초기 청크가 늘고, 둘 다 lazy면 첫 화면이 왕복 1회 뒤에 뜬다 — 0005가 지불을 거부했던 바로 그 왕복이다. **단 이번엔 조건이 다르다**: `_authed.beforeLoad`가 `GET /auth/me` 네트워크 왕복을 어차피 수행하므로, 라우터가 그 왕복과 청크 로드를 **병렬로** 진행한다면 lazy의 대가가 숨겨진다.

**추측으로 정하지 않는다.** 구현 시 워터폴로 실측해 결정하고, 그 측정으로 0005 §결정 3의 근거를 갱신한다.

# ADR — 아키텍처 결정 기록

프론트엔드 범위의 구현 결정을 기록한다. 파일명 `NNNN-제목.md` 연번, [TEMPLATE.md](TEMPLATE.md) 사용.

## 무엇이 ADR감인가

**설계서가 규정하지 않은, 뒤집기 비용이 있는 구현 선택**이 ADR감이다. 예:
- 스토어 슬라이스 분할 방식, 오버레이 렌더 전략(2D vs WebGL), IndexedDB 스키마, 테스트 더블 설계 같은 구현 재량 사항
- 설계서가 "협의 후 결정"으로 열어둔 항목의 확정 결과 (예: 텔레메트리 수신 경로)

**ADR이 아닌 것** — 흔한 착각 주의:
- 설계서 v2.1이 이미 규정한 사항 (그건 규범이지 결정이 아니다 — 절 번호를 인용하면 끝)
- 수치 변경 (수치의 유일한 출처는 `.claude/CLAUDE.md` §4 — 변경은 설계서 개정 절차)
- 확정 전제 3건(Chromium 한정·한국 사용자·SWA 유지)을 뒤집는 제안 (설계서 부록 C.2 개정 절차로 — ADR로 우회 금지)
- 인프라 결정 (G-1 인프라 타깃 ADR은 **인프라 담당 소유** — 여기가 아니라 그쪽 채널. RP-2에 따라 "설계서 영향 절"만 명기해 전달)

## 절차

1. 결정이 필요해진 시점에 `상태: 제안`으로 작성 — 맥락과 대안을 **결정 전에** 적는 것이 핵심 (사후 정당화 방지).
2. 팀 합의 후 `상태: 승인` — 합의 채널·날짜 기록.
3. 뒤집을 때는 삭제하지 않고 `상태: 폐기(→ NNNN)` — 새 ADR이 옛것을 참조. 왜 뒤집었는지가 가장 값진 기록이다.

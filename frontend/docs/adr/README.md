## 무엇이 ADR감인가

**뒤집기 비용이 있는 구현 선택**이 ADR감이다.

- 설계서가 규정하지 않은 구현 재량 사항 — 도구 선택, 상태 관리 분할 방식, 테스트 더블 설계 등
- 설계서가 "협의 후 결정"으로 열어둔 항목의 확정 결과
- **설계서가 규정한 것을 다르게 정하는 경우** — **설계서는 프론트 담당 재량**이므로 이건 이탈이 아니라 **개정**이다. ADR로 근거를 남기고, 승인 시 설계서 해당 절을 같이 갱신한다. 근거를 ADR에 남기는 이유는 허락을 받기 위해서가 아니라 **왜 바꿨는지가 나중에 필요하기 때문**이다. 0001·0002가 이 경우다

**ADR이 아닌 것**

- 설계서가 이미 규정했고 **그대로 따르는** 사항 — 그건 규범이지 결정이 아니다. 절 번호를 인용하면 끝난다
- 되돌리는 데 비용이 없는 선택 — 코드 리뷰에서 정하면 된다
- 백엔드·인프라 결정 — **소유가 여기가 아니다.** 해당 채널로 보내고, 프론트에 영향이 있으면 "영향 받는 절"만 명기해 전달한다

## 현재 규범

| 대상 | 문서 |
|---|---|
| 기술 스펙 (버전·Node·빌드·타입) | `docs/frontend_architecture_v3.7.md` — **저장소 루트의 `docs/`이며 `.gitignore` 대상이라 커밋되지 않는다.** 팀 공유가 필요한 내용은 아래 architecture 문서가 발췌·기록한다 |
| 적용 설계 (툴체인) | [../architecture/toolchain.md](../architecture/toolchain.md) |
| 적용 설계 (레이어·경계) | [../architecture/layers.md](../architecture/layers.md) |

**설계서는 프론트 담당 소유다.** 따라서 기술 스펙을 바꾸는 결정은 위 ADR로 하고, 채택된 내용은 설계서에 반영한다.

확정 전제 — 프론트엔드 호스팅은 **Azure SWA 유지**, 인프라 타깃은 **AKS**. 이 둘은 인프라와 맞물려 있으므로 뒤집으려면 인프라 쪽과 함께 정한다.

## 절차

1. 결정이 필요해진 시점에 `상태: 제안`으로 작성 — **맥락과 대안을 결정 전에 적는 것이 핵심이다** (사후 정당화 방지).
2. 확정되면 `상태: 승인` — 날짜와 결정자를 기록한다. 설계서 해당 절도 같은 PR에서 갱신한다.
3. 뒤집을 때는 삭제하지 않고 `상태: 폐기(→ NNNN)` — 새 ADR이 옛것을 참조한다. **왜 뒤집었는지가 가장 값진 기록이다.**

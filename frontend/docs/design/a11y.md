# 접근성 정책

> **최종 갱신** 2026-08-30 (D26 — §1.5 「그린 상자 ≠ 타겟」 · §2.5 드롭다운 목록 크기 · §4 색만으로 전달 금지에 `Select` 행 추가 / 그 앞은 §2.6 확대의 세 경로 신설 — D24) · **문서 소유** 프론트 담당
>
> 수치마다 **출처와 확인 등급**을 붙인다. 등급은 셋이다 — **1차 공식**(표준 문서·공식 문서 원문) /
> **2차 자료**(널리 재현되지만 1차 근거를 못 찾음) / **미확인**.
> 이 구분을 생략하면 근거가 약한 규칙과 강한 규칙이 같은 무게로 읽힌다.

## 1. 터치 타겟

### 1.1 표준 원문

| 출처 | 수치 | 등급/성격 | 확인 |
|---|---|---|---|
| **WCAG 2.2 SC 2.5.8** Target Size (Minimum) | **24 × 24 CSS px** | **Level AA (필수)** | 1차 — [w3.org](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) |
| **WCAG 2.2 SC 2.5.5** Target Size (Enhanced) | **44 × 44 CSS px** | **Level AAA (권고)** | 1차 — [w3.org](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) |
| Apple HIG | 44 × 44 pt | 플랫폼 권고 | 1차 — [developer.apple.com](https://developer.apple.com/design/tips/) |
| Material Design 3 / Android | 48 × 48 dp, 간격 8 dp 이상 | 플랫폼 권고 | 1차 — [support.google.com](https://support.google.com/accessibility/android/answer/7101858?hl=en) |
| **KRDS** 버튼 · 링크 | 마우스 17 × 17 px · **터치 44 × 44 px 이상** "권장한다" | 국내 정부 가이드 | 1차 — [krds.go.kr 버튼](https://www.krds.go.kr/html/site/component/component_05_02.html) |
| **KWCAG 2.2** 6.1.3 (조작 가능) | 대각선 **6.0 mm 이상** "바람직하다" | 권고 | **2차** — [a11ykr.github.io 미러](https://a11ykr.github.io/kwcag22/). 커뮤니티 GitHub Pages 사본이지 표준 원문 호스트가 아니다. 1차(TTA/국립전파연구원 고시 원문)로 교체 전까지 등급을 낮춰 둔다 |

### 1.2 정정 2건

**① 「44px = WCAG」는 부정확하다.**
`src/shared/ui/README.md` 토큰 표가 44px을 *"제품 문서의 접근성 요구"* 로만 적는데, 실제 출처는 **WCAG AAA(2.5.5) + Apple HIG 44pt + KRDS 터치 44px** 세 가지의 수렴이다. **WCAG AA 최저선은 24px**이다. 이 구분은 실무에서 가장 자주 뒤섞여 인용된다. → **정정 주체: [implementation-plan.md](implementation-plan.md) C2b**(그 파일의 44px·iOS 서술을 이 절 기준으로 고친다).

**② 「KWCAG 2.2 = 44×44 CSS px」는 사실이 아니다.**
KWCAG 2.2에는 WCAG 2.5.8에 대응하는 **타겟 크기 검사항목이 없다.** 관련 규정은 기존 6.1.3의 *"대각선 방향의 길이를 6.0mm 이상으로 제공하는 것이 바람직하다"* 뿐이고, **물리 mm 단위이지 CSS px가 아니다.** 그렇게 요약한 2차 자료가 있으나 1차 지침 본문에 근거가 없다 — **인용하지 않는다.**

### 1.3 SC 2.5.8의 예외 (AA)

AA는 다섯 가지 예외를 둔다. 그중 실무에서 실제로 쓰이는 것은 **Spacing**이다:

> "Undersized targets … are positioned so that if a **24 CSS pixel diameter circle** is centered on the bounding box of each, the circles do not intersect another target or the circle for another undersized target"

나머지: Equivalent(같은 페이지의 다른 컨트롤로 가능) · Inline(문장 안이거나 line-height에 크기가 제약됨) · User Agent Control(작성자가 크기를 바꾸지 않음) · Essential.

⚠️ **AAA(2.5.5)의 예외 목록은 AA와 다르다** — AAA에는 **Spacing 예외가 없다.**

### 1.4 목업 판정

| 목업 실측 | AA(24px) | AAA(44px) | Apple 44pt | KRDS 44px |
|---|---|---|---|---|
| 16px (슬라이더 썸) | **불합격** — spacing 예외에 기대야 함 | 불합격 | 불합격 | 불합격 |
| 19~22px (체크박스 · 스위치) | 불합격~경계 | 불합격 | 불합격 | 불합격 |
| 28~38px (뒤로 · 전송 · 필터) | 합격 | 불합격 | 불합격 | 불합격 |

**하단 탭바처럼 타겟이 붙어 있는 구조에서는 spacing 예외를 쓸 수 없다** — 24px 지름 원이 서로 교차한다.

### 1.5 결정

**44px 계약을 유지한다** (`--spacing-tap: 2.75rem` → `min-h-tap`). 근거 셋이 수렴하고, AA(24px)는 어차피 포함된다.

⚠️ **계약의 대상은 「그린 상자」가 아니라 「포인터를 받는 영역」이다.** WCAG 는 target 을 *포인터
동작을 받는 영역*으로 정의하지 보이는 그래픽으로 정의하지 않는다. 그래서 **밀도 요청과 이 계약은
양자택일이 아니다** — 상자를 36px 로 그리고 의사요소로 히트 영역만 44px 로 되돌리면 둘 다 지킨다.
현재 이 분리를 쓰는 곳은 셋이다: `shared/ui/Button` 의 `sm`([D24 이전, 2026-08-29](decisions.md)) ·
`pages/chat/ui/ChatPage` 헤더 버튼 · `shared/ui/Select` 의 `compact`([D26](decisions.md#d26-드롭다운의-목록이-트리거를-따라간다--체크-아이콘-제거--접힌-상자-36px)).

🚨 세 곳 모두 **높이 조각과 의사요소가 짝**이다. 하나만 빠지면 화면에는 아무 변화가 없이 타겟만
36px 이 된다 — 눈으로는 못 잡으므로 각 컴포넌트의 테스트가 짝으로 고정한다. **이 분리를 새로
쓰는 곳이 생기면 여기 한 줄을 더하고 테스트를 함께 만든다.**

⚠️ 이 수법을 **목록의 인접 행에는 쓸 수 없다** — 넘친 히트 영역이 서로 겹쳐 이웃의 클릭을 뺏는다.
그래서 `Select` 의 팝업 항목은 44px 그대로다.

부수 효과 — 하단 탭바에 **아이콘 + 텍스트 라벨을 병기**하면([layout.md](layout.md)) 탭 높이가 자연히 44px 이상이 되어 이 요구를 함께 만족한다.

## 2. 글자 크기

### 2.1 KRDS 타이포그래피 (1차 — [krds.go.kr](https://www.krds.go.kr/html/site/style/style_03.html))

> "본문 폰트 크기는 모든 사용자가 쉽게 읽을 수 있도록 **최소 16px 이상**으로 설정한다."
> "줄 간격(line-height)은 가독성과 접근성을 위해 **최소 150% 이상**으로 설정한다."

KRDS Body 스케일: `body-large 19` · **`body-medium 17`(기본 본문)** · `body-small 15` · `body-xsmall 13` — 전부 line-height 150%.

**주목** — KRDS에도 13px·15px 토큰이 **있다.** 즉 "본문은 16px 이상"이지 "모든 텍스트가 16px 이상"이 아니다. 어느 텍스트가 *본문 역할*인지로 갈린다. 다만 **12px 미만은 KRDS 스케일에 대응 토큰 자체가 없다.**

### 2.2 WCAG는 최소 글자 크기를 규정하지 않는다

| SC | 등급 | 요구 |
|---|---|---|
| **1.4.4** Resize Text | AA | 텍스트를 **200%** 까지 확대해도 내용·기능 손실이 없을 것 |
| **1.4.12** Text Spacing | AA | line-height 1.5배 · 문단 간격 2배 · 자간 0.12배 · 어간 0.16배로 바꿔도 손실 없을 것 |
| **1.4.8** Visual Presentation | AAA | 줄당 80자 이하 (**CJK는 40자**) · 줄 간격 1.5배 이상 |

**WCAG 어디에도 "본문 최소 16px" 규정은 없다.** 확대와 간격 조정을 견디는지만 본다. 따라서 16px 계약의 1차 근거는 **KRDS**다.

CJK 최소 글자 크기에 대한 **W3C 급 권고는 존재하지 않는다**(확인함). WCAG가 CJK를 명시하는 유일한 지점은 1.4.8(AAA)의 줄당 40자이며, 그 근거로 *"CJK characters are approximately twice as wide as non-CJK characters"* 라고만 서술한다.

### 2.3 iOS 입력 필드 자동 확대 — **근거 등급 주의**

`src/shared/ui/README.md` 토큰 표의 입력 필드 행이 *"iOS Safari 는 그보다 작은 입력에 포커스 시 화면을 자동 확대한다"* 고 **단정**한다(→ C2b에서 2차 자료 등급을 붙인다).

**확인 결과: Apple / WebKit의 1차 공식 문서를 찾지 못했다.** 널리 재현되고 2026년 현재도 여러 프로젝트에서 활성 이슈로 보고되지만, 근거는 전부 2차 자료다([CSS-Tricks](https://css-tricks.com/16px-or-larger-text-prevents-ios-form-zoom/) · [Defensive CSS](https://defensivecss.dev/tip/input-zoom-safari/)).

**→ 규칙은 유지하되 1차 근거를 KRDS 16px로 둔다.** 두 기준이 같은 방향을 가리키므로 결론은 바뀌지 않는다. 문서에는 등급을 표시한다.

### 2.4 ⚠️ 회피책 금지

`user-scalable=no` / `maximum-scale=1`로 iOS 확대를 막는 것은 **WCAG 1.4.4 (AA) 위반**이다.

> MDN 경고: "Disabling zooming capabilities … prevents people experiencing low vision conditions from being able to read and understand page content. … **WCAG requires a minimum of 2× scaling**; however, the best practice is to enable a 5× zoom."
> — [MDN viewport meta](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport) (1차)

**반드시 입력 필드 폰트를 16px 이상으로 올려 해결한다.**

⚠️ **이 절은 확대의 「세 경로」 중 둘만 다뤘다** — §2.6 이 세 번째(더블탭)를 채운다.
그 빈칸이 실제 결함으로 드러났다(사용자 리포트 2026-08-30).

### 2.5 결정 — 현행 스케일 유지

| 역할 | 값 | 근거 |
|---|---|---|
| 주 본문 | **16px** + `ink` | KRDS 본문 최소 16px |
| 보조 문구 | 14px + `ink-soft` | KRDS body-small(15) 인근 |
| 캡션 · 라벨 | 12px + `ink-soft` | 짧은 것만 |
| 입력 필드 | **16px 미만 금지** | KRDS + iOS 동작(2차). **2026-08-30 부터 규범이 아니라 기본값이다** — `styles.css` `@layer base` 의 `input, textarea, select { font-size: 1rem }` 이 바닥을 깔고 빌드 게이트가 그 선언을 지킨다([D24](decisions.md#d24-모바일의-의도치-않은-확대만-끈다--더블탭은-컨트롤에서만-포커스-확대는-기본값으로)). 이 행은 여전히 **「내리지 마라」**를 말한다 — 하한이지 고정값이 아니다 |
| 드롭다운 | 위 세 역할을 따른다 (16 / 14) | **[D22](decisions.md#d22-드롭다운을-네이티브-select-에서-자체-컴포넌트로-옮긴다)** — 이 규범의 **대상이 아니다**. 아래 ⚠️<br>**열린 목록도 같은 값을 쓴다** — 컴포넌트가 고정하며 호출부 조상에서 상속하지 않는다([D26](decisions.md#d26-드롭다운의-목록이-트리거를-따라간다--체크-아이콘-제거--접힌-상자-36px)). 고치기 전에는 같은 컴포넌트의 목록이 자리에 따라 12·14·16px 로 갈렸다 |
| 행간 (CJK) | 1.5~1.6 | KRDS 150% · WCAG 1.4.12 1.5배를 모두 상회 |

**목업 대비** — 목업은 주 본문 13~14px · 보조 11~12px · 캡션 9.6~11.8px이고 **12px 미만 `font-size` 선언이 50건 / 전체 111건**이다(저장소 안 정적 사본 실측 — 초판의 「119건」은 저장소 밖 프로토타입 기준이라 이 브랜치에서 재현되지 않아 교체했다). **목업 크기를 한 단계 올려 적용한다.** 목업의 밀도는 390pt 프레임을 데스크톱 캔버스에 1:1로 그린 데서 온 것이라 실기기 판독성 검증을 거치지 않았다.

> 행간 1.6은 KRDS 150%·WCAG 1.5배의 **여유분**이다. "1.6이어야 한다"는 근거 표준은 없다(1.5가 공식 하한).

⚠️ **이 규범의 대상은 「입력 필드」다 — 모든 컨트롤이 아니다.** iOS 자동 확대는 **텍스트 입력
포커스**에서 일어나고(§2.3), KRDS 16px 은 §2.1 이 이미 정리했듯 *"본문은 16px 이상"이지 "모든
텍스트가 16px 이상"이 아니다*(KRDS 스케일 자체에 13·15px 토큰이 있다).

그래서 [D22](decisions.md#d22-드롭다운을-네이티브-select-에서-자체-컴포넌트로-옮긴다) 의 드롭다운은
**이 규범의 적용 대상이 아니다** — 트리거가 `<button>` 이라 확대 조건에 애초에 걸리지 않는다.
콘텐츠 안에 홀로 놓인 드롭다운은 14px 를 쓴다. 그 자리들에서 드롭다운이 옆의 제목·본문보다 커져
위계가 뒤집혀 있었다(사용자 리포트 2026-08-29).

🚨 **이것을 「16px 규칙의 우회」로 읽지 않는다.** 우회는 §2.4 가 금지한 `user-scalable=no` 쪽이고,
그건 텍스트 입력을 작게 둔 채 **브라우저의 대응을 막는** 것이다. 텍스트 `<input>`·`<textarea>` 의
16px 계약은 그대로다 — 이 저장소에 그것을 어기는 자리는 없다.

### 2.6 확대의 세 경로 — 무엇을 남기고 무엇을 끄는가

**[D24](decisions.md#d24-모바일의-의도치-않은-확대만-끈다--더블탭은-컨트롤에서만-포커스-확대는-기본값으로)** (2026-08-30, 사용자 리포트). 이 문서는 오래 확대를 **두 각도**로만 다뤘다 —
§2.3 「포커스 자동 확대」와 §2.4 「회피책 금지」. **세 번째 경로인 더블탭 확대가 문서에도
코드에도 없었고**(저장소 전체 `touch-action` 0건), 그것이 실제 증상이었다.

| 확대 경로 | 누가 시작하나 | 판정 | 장치 |
|---|---|---|---|
| **핀치 확대** | 사용자 | ✅ **유지** — WCAG 1.4.4(AA) 200% 를 실제로 충족시키는 주 수단 | `index.html` 이 `user-scalable`·`maximum-scale` 을 넣지 않는다(§2.4) |
| **브라우저 줌 · iOS 페이지 줌 설정** | 사용자 | ✅ **유지** | 아무것도 하지 않는다 |
| **본문 텍스트 위 더블탭 확대** | 사용자 | ✅ **유지** — 저시력 사용자의 실제 확대 수단이다 | `touch-action` 을 **`body` 에 걸지 않는다** |
| **컨트롤 위 더블탭 확대** | 아무도 — 항상 오작동 | ❌ **차단** | `styles.css` `@layer base` — `button, a, label, summary, input, textarea, select, [role="option"]` 에 `touch-action: manipulation` |
| **입력 포커스 자동 확대(iOS)** | 아무도 — 항상 오작동 | ❌ **차단** | 입력 16px(§2.5) + base 레이어 기본값 + 빌드 게이트 |

**왜 컨트롤 위 더블탭은 「항상 오작동」인가** — 버튼이나 체크박스를 두 번 눌러 확대하려는
사용자는 없다. 반대로 **텍스트 입력칸은 두 번 탭하는 것이 가장 흔한 조작이다**(포커스 →
캐럿 이동, 혹은 키보드가 늦어 한 번 더). 그 두 번째 탭이 확대로 해석되는 것이 리포트의 실체였다.

**근거 등급 1차** — CSS Touch Action Level 1 이 `manipulation` 을 이렇게 정의한다:

> "enable panning and pinch zoom gestures, but disable additional non-standard gestures
> such as double-tap to zoom"
> — [w3.org/TR/pointerevents](https://www.w3.org/TR/pointerevents/#the-touch-action-css-property)

**핀치가 명시적으로 유지된다.** §2.3 의 iOS 자동 확대(2차 자료뿐)와 달리 이쪽은 1차 근거가 있다.

🚨 **§2.4 의 우회로 읽지 않는다.** §2.4 가 금지한 것은 **사용자가 스스로 하는 확대**를 막는
것이고, 여기서 끄는 것은 **사용자가 한 적 없는 확대**다. 층위가 다르다. 판별 기준은 위 표의
「누가 시작하나」 열이다 — **「사용자」 행을 하나라도 ❌ 로 바꾸는 제안은 §2.4 위반이다.**

부수 이득 — 더블탭 대기(약 300ms)가 사라져 컨트롤의 단일 탭 반응이 빨라진다.

| **목록 시맨틱** | 납부 예정 · 카테고리 · 체크리스트 · 타임라인처럼 **반복 행**이 있는 자리를 `<ul>`/`<li>` 로 낼지. 실측: 목업 6개에 `<ul>`·`<li>` 가 **0건**(전부 `<div>`)이고 이 문서에도 규정이 없다. 걸려 있는 것은 스크린리더의 *"목록, 항목 N개"* 안내와 항목 단위 이동이다.<br>**5개 화면이 같은 구분선 리스트를 요구하므로**(s1 2곳 · s2 2곳 · s3 · s5 · s6) 공용 `DividedList` 를 만들 때 이 결정이 먼저 필요하다 — 나중에 뒤집으면 7곳이 함께 바뀐다. 제목 계층(§4)과 같은 종류의 판단이지만, 제목과 달리 **`<p>`→`<h2>` 처럼 명확한 WCAG 실패 조항이 대응되지 않아** 별도로 남긴다 |

# 03. 적용 로드맵 — 툴체인 · FSD 이관 · M1~M5 WBS

설계서 v2.1 부록 D.2의 마일스톤을 `frontend/` 작업 단위로 분해한다. 완료 기준은 전부 §7.5 수용 기준([04 문서](04_검증_수용기준.md) 추적표)에 연동한다.
게이트 의존: **M2 ← G-4 · M3 ← G-3 · M5 ← G-1** ([01 문서](01_전제와_착수게이트.md)). M1·M4는 게이트 무의존.

> ⚠️ 아래 §1(툴체인)과 §2(이관)는 전부 **명시적 승인 후에만** 실행한다 — `package.json`·`tsconfig*`·`vite.config.ts`·의존성·디렉토리 이관이 승인 대상이다.

## §1. 툴체인 정비 (격차 A-1~A-5 해소 — M1 착수 전 단일 PR 권장)

### 1-1. TypeScript 다운그레이드 (A-1)

```bash
npm i -D typescript@~6.0.3   # ~ 레인지 그대로 package.json에 기록되는지 확인
```

- 근거(§1): npm에 6.x dist-tag가 없어 `~6.0.3`이 유일한 6.x 고정 수단 (2026-08-17 npm 실측 3회 일치).
- 검증: `npx tsc --version` → 6.0.3, 기존 소스 `tsc -b` 통과.

### 1-2. Project References 재편 (A-2·A-3)

목표: `shared/protocol`·`shared/workers`의 **DOM 타입 비의존**(§6.1)을 컴파일러가 강제.

| 파일 | 역할 | 핵심 |
|---|---|---|
| `tsconfig.json` | 참조 전용 셸 | `"files": []` + `references: [app, worker]` |
| `tsconfig.app.json` | 앱 본체 (DOM) | 현행 옵션 승계 + `composite: true`, worker·protocol 제외 |
| `tsconfig.worker.json` | workers + protocol | `lib: ["ES2022", "WebWorker"]` — **DOM 없음**, `composite: true` |

- scripts: `"build": "tsc -b && vite build"` (§6.4 — `--noEmit`은 참조 프로젝트를 빌드하지 않아 격리 검사 무효).
- `composite: true`의 선언 출력(`outDir`·`tsBuildInfoFile`)은 `node_modules/.cache/` 하위로 배출 (산출물 오염 방지).
- 재편은 **M1 디렉토리 생성과 같은 PR**이 자연스럽다 (이관 전에는 대상 폴더가 없음).

### 1-3. build.target 명시 (A-4)

```ts
build: { target: ["chrome111", "edge111"] }   // §6.3 지원 매트릭스 SSOT — Vite 기본값 위임 금지
```

하한 변경은 분기별 StatCounter 실측만(§6.3). 임의 상향은 기각된 이력이 있다 (검토 보고서 v3.0).

### 1-4. 의존성 설치 (A-5)

```bash
npm i -E zustand@5.0.15                    # §1 확정 버전
npm i -E @mediapipe/tasks-vision@1.0.1     # 락파일 고정 — 업그레이드 시 §7.3 회귀 필수
npm i -D dependency-cruiser@^18            # §6.1.1 CI 게이트
```

- **`-E`(--save-exact) 필수** (재발 방지): `npm i pkg@x.y.z`는 save-prefix 기본값 때문에 `^x.y.z`로 기록된다. 레인지를 직접 쓰는 typescript(`~6.0.3`)만 `-E` 불요.
- WS SDK(socket.io 등)는 **어떤 이유로도 추가 금지** (§1 — 브라우저 네이티브 WebSocket API).

### 1-5. WASM·모델 self-hosting (M3 전 · §6.2)

- `node_modules/@mediapipe/tasks-vision/wasm/` → `frontend/public/mediapipe/wasm/`.
- pose_landmarker `.task` Lite·Full을 공식 배포처에서 받아 `frontend/public/mediapipe/models/` + SHA-256 기록. Heavy는 제외.
- CDN 경로 하드코딩 금지(P0) — `FilesetResolver.forVisionTasks('/mediapipe/wasm')` 형태의 self-host 경로.
- SWA 서빙 요건은 A-6(`staticwebapp.config.json`)과 연동 — mimeTypes `.task: application/octet-stream`, immutable 캐시.

### 1-6. staticwebapp.config.json (M5 전 · A-6)

§6.4.1 표 그대로 작성. CSP의 API 호스트 값은 환경별 빌드의 `VITE_API_BASE`와 동일 값 — **런타임 오리진 스위칭 구현 금지**(§1·§6.4, 빌드타임 정적 치환).
prod 값은 실측 확정 후보가 있고 **staging 값은 미확정** ([05 문서](05_리스크_오픈이슈.md) I-9).

## §2. FSD 이관 (M1)

목표 구조·이관 매핑·import 규칙의 상세는 [architecture/directory-structure.md](../architecture/directory-structure.md)가 담당한다. 여기는 실행 순서만:

1. 신설 골격 생성(빈 `index.ts` 포함) + tsconfig 재편(§1-2)을 같은 PR로.
2. 기존 파일 `git mv`(이력 보존) 이관 + import 경로 수정 + 폴더 README 갱신(구판 수치 정정 포함 — 격차 B-3). **한 번에 한 폴더씩**, 테스트 파일 동반 이동.
3. `shared/protocol` 구현: Envelope 타입(§3.1) → 24B 헤더 코덱(§3.2) → 수신 가드(§3.5) → 골든 벡터 상수.
4. depcruise 규칙 4종(`no-cross-feature`·`no-upward-import`·`no-slice-internals`·`worker-no-dom`, §6.1.1) 설정 + 로컬 `depcruise --validate` 통과.

**이관 중 재발 방지 3칙**
- 이관은 파일 이동이지 기능 추가가 아니다 — 이관 PR에 동작 변경을 섞지 않는다 (리뷰 가능성).
- `shared/protocol`에 `ws.send`·소켓 참조를 두지 않는다 — 헤더 작성과 send는 메인 스레드 `features/realtime` 소유 (§4.4.0, P0).
- 수치는 전부 `shared/config` 상수로 — 매직넘버 금지, 값의 규범 출처는 설계서 절 번호를 주석으로.

## §4. 크리티컬 패스

```
[승인] 툴체인(M1-1) → M1 ──(G-4 합의 = M2-0)──→ M2 ─┐
        G-3 대조(병행 요청) ────────────────────────┴→ M3 → M4 → M5 ← G-1 ADR + 인그레스 기동
```

- M2와 M3-0(자산 준비)은 병행 가능. M4는 M3와 부분 병행 가능(룰 엔진 순수 함수는 픽스처만 있으면 됨).
- **최우선 착수 3건**: ① 툴체인 승인 ② G-3 요청 발신 ③ G-4 카탈로그 합의 — 전부 외부 의존이라 대기 시간이 크리티컬 패스에 직결된다.
- M5 실질 선행: G-1 ADR 문서화 + 인그레스 기동·애노테이션 확인 + staging 환경값 확정 ([05 문서](05_리스크_오픈이슈.md) I-8·I-9).

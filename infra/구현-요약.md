# Infra 상세 설정 완료 요약 (2026-08-13 세션)

> 참고: 루트 `docs/`는 `.gitignore`에 걸려 있어서(팀 공용 아님, 개인 기록용) 이 파일은 `infra/` 바로 아래 뒀다.
> `infra/docs/`처럼 "docs"라는 이름의 하위 폴더를 만들면 `.gitignore:91`의 `docs/` 패턴이 경로 어디서든
> 매칭돼서 똑같이 무시된다 — `infra/`에 직접 두는 이유.

## 0. 이번 세션이 왜 필요했나

이전 세션에서 `infra/`(Bicep 8모듈 + k8s/ArgoCD)가 AKS 기반으로 짜였는데, `docs/설계/*` 설계 문서들은
"AKS 재검토 후 Container Apps로 최종 확정"이라고 되어 있어서 설계 문서와 실제 코드가 정반대였다.
확인 결과 **AKS로 최종 확정**(포트폴리오 사유 — 로컬 k3s/ArgoCD는 이미 해봤지만 매니지드 클라우드 K8s는
처음). GPU 노드풀은 보류(CPU 추론 가정, `backend/pyproject.toml`에 `onnxruntime`도 아직 없어서 실제
필요 여부 자체가 미확정 — ml 레포 실측 후 재검토).

이후 Bicep 모듈 8개(`infra/bicep/modules/*.bicep`) 전체를 하나씩 상세 옵션까지 결정했다. 매 변경마다
`az bicep build --file infra/bicep/main.bicep`로 검증(전부 통과 상태) — 단, **`az deployment group
create`/`what-if`는 아직 한 번도 안 돌렸다. 실제 Azure 리소스는 하나도 안 만들어진 상태**다.

  k8s 매니페스트(`secretproviderclass.yaml`)가 이미 이 방식을 전제로 짜여 있었는데 애드온이 빠져있던
  버그를 발견해서 수정함
- Workload Identity federated credential이 `staging`/`production` 네임스페이스 각각에 대해 생성되도록
  수정(원래는 어느 네임스페이스와도 안 맞는 기본값 하나만 있던 버그)
- **(2026-08-13 추가) ArgoCD Image Updater용 전용 identity** — `imageUpdaterIdentity` UAMI + `argocd`
  네임스페이스 `argocd-image-updater` ServiceAccount용 federated credential + ACR AcrPull 롤 할당.
  backend Identity와 분리한 이유: "백엔드 워크로드 identity"와 "GitOps 컨트롤러 identity"는 관심사가

## 6. Ingress / 도메인 / TLS 결정 (2026-08-13, 할일.md P3)

처음엔 Azure 자동 DNS 라벨이 Public IP 1개당 1개 이름만 지원한다는 이유로 ingress-nginx를
staging/production 각각 별도 설치(2벌)하는 구조로 짰는데, "nginx 2개 꼭 필요한가"는 피드백을 받고
재검토해서 **1벌로 단순화**했다. 근거: `frontend-ci.yml`은 PR 프리뷰든 프로덕션 배포든 `VITE_API_BASE`
시크릿 하나만 항상 쓴다 — 즉 브라우저(Static Web App)가 staging 백엔드를 직접 호출하는 경로 자체가
없고, staging은 `backend` 브랜치 머지 전 팀 내부 사전 점검용일 뿐이라 예쁜 공인 도메인이나 별도
컨트롤러가 필요 없다.

- **도메인**: 실도메인 구매 대신 AKS/Azure LoadBalancer 자동생성 DNS 라벨(무료) — **production만**
  라벨을 받고(`aicoach-production.koreacentral.cloudapp.azure.com`), **staging은 같은 컨트롤러의 같은
  공인 IP를 `nip.io`로 재사용**(`<IP를-하이픈으로-치환>.nip.io`, IP가 바뀌면 재조합 필요 — 내부
  점검용이라 영향 적음). DNS 이름 레이블 범위는 ACR과 동일하게 No Reuse.
- **TLS**: cert-manager + Let's Encrypt 운영 ACME 자동 발급으로 확정(`nip.io`도 실제 공인 DNS라 HTTP-01
  challenge 그대로 통과). 컨트롤러가 1개라 ClusterIssuer도 **`letsencrypt-nginx` 1개**로 충분.
- ingress-nginx는 **클러스터에 1벌만** 설치(Public IP 1개, `ingressClassName: nginx` 공용). staging/
  production Ingress는 네임스페이스는 분리 유지하되 같은 ingress class·같은 Issuer를 공유하고 host만
  다르다.
- `infra/k8s/overlays/backend-production/ingress.yaml`은 호스트 확정 완료. `backend-staging/ingress.yaml`은
  구조만 완료하고 호스트는 `<STAGING_NIP_IO_HOST_TBD>`로 남김(ingress-nginx 설치 후 실제 공인 IP가 나와야
  알 수 있어서 — P1 이후 채울 항목, 할일.md P3 실행 단계 1번).
- `infra/k8s/cert-manager/`(README + `cluster-issuer.yaml` 1개) 신규 생성.
- `infra/할일.md`의 `VITE_API_BASE` GitHub Secret 값도 결정된 프로덕션 호스트로 갱신함.

## 5. 아직 검증 안 된 것

- `az deployment group create`/`what-if` 실행 자체를 아직 안 함 — Bicep 문법은 맞지만 실제 배포 성공은
  미검증(특히 Azure OpenAI 모델 배포는 구독 쿼터에 따라 실패 가능)
- `infra/.env`의 `CLUSTER_ADMIN_OBJECT_IDS`가 비어있음 — 채우기 전엔 AAD RBAC 클러스터 admin이 아무도
  없는 상태로 배포됨(비상 접근은 가능하지만)
- Azure 자동 DNS 라벨이 실제로 몇 분 내 반영되는지, cert-manager HTTP-01 challenge가 nginx-staging/
  nginx-production 컨트롤러 분리 구조에서 정상 통과하는지 — 둘 다 실배포 후 라이브 확인 필요

## 7. 2026-08-13 추가 세션 — app-of-apps/ConfigMap 리뷰 + Ansible 부트스트랩

`infra/k8s/apps/` 구조와 ConfigMap 흐름을 다시 보다가 실제 버그 2개를 발견해서 고쳤다(설계 변경 아니고 버그 수정):

1. **`MODEL_VERSION` ConfigMap이 값이 바뀌어도 롤아웃을 안 일으킴** — `deployment.yaml`/`cronjob.yaml`이
   `envFrom: configMapRef`로 고정 이름(`model-version`)을 참조하는데, ArgoCD가 ConfigMap 값만 갱신해서는
   이미 떠있는 Pod가 재기동되지 않음(K8s가 env var 참조는 감지 안 함). `infra/k8s/base/{backend,rag-cronjob}/`
   둘 다 `configmap-model-version.yaml`(정적 YAML)을 지우고 `configMapGenerator` + `model-version.env`로
   교체 — 값이 바뀌면 해시 서픽스가 붙은 새 ConfigMap이 생기고 kustomize가 참조도 자동으로 갱신해서
   Deployment/CronJob이 새 리비전을 받는다. Key Vault CSI 시크릿(openai-key 등)과는 무관한 별개 문제.
2. **`root-app.yaml` 자기참조** — `infra/k8s/apps/root-app.yaml`이 자기 자신이 관리하는 폴더
   (`spec.source.path: infra/k8s/apps`) 안에 있었음. `prune: true`라 폴더 구조가 바뀌면 root-app이 스스로를
   지울 수 있는 구조라 `infra/k8s/root-app.yaml`(apps/ 폴더 밖)로 이동 — k3s-repo 원본 패턴(root-app이

**OIDC federated credential 불일치(AADSTS700213) 트러블슈팅**: `infra-deploy.yml`의 `pull_request` 트리거

## §14. Workload Identity 로그인 방식 최종 수정 + 검증 완료 (2026-08-14, 세션 마무리)

`fetch-model` Init Container가 `Init:CrashLoopBackOff`로 계속 죽고 있어서 로그를 보니, `az login --identity`
자체가 틀린 진입점이었다. 시도 순서:

1. `az login --identity`(client-id 없이) → `ERROR: Multiple user assigned identities exist` — az CLI가
   Workload Identity(OIDC federated token 교환)가 아니라 노드 IMDS 경로로 identity를 찾으려다, 노드에
   붙은 identity가 여러 개라 어느 걸 쓸지 특정 못 해서 실패.
2. `az login --identity --client-id "$AZURE_CLIENT_ID"`(커밋 `15572fe`) → `ERROR: Identity not found` —
   여전히 IMDS 경로라, backend identity(UAMI)가 노드에 물리적으로 안 붙어있어서(Workload Identity는 애초에
   그런 방식이 아님) 못 찾음. 에러 문구만 바뀌었을 뿐 근본 원인은 그대로였음.
3. `az login --help`로 정확한 플래그를 다시 확인한 뒤, `--federated-token`(OIDC 토큰 교환 전용 플래그,
   GitHub Actions의 `azure/login@v2`와 동일 메커니즘)으로 전환(커밋 `971ec6e`):
   ```
   az login --service-principal \
     --username "$AZURE_CLIENT_ID" \
     --tenant "$AZURE_TENANT_ID" \
     --federated-token "$(cat "$AZURE_FEDERATED_TOKEN_FILE")"
   ```
   **`kubectl logs`로 실제 로그인 성공까지 확인** — `az account show` 출력 JSON의 `"user"` 필드가
   `{"name": "2a104ab0-1f52-480c-89aa-57306cf7f85b", "type": "servicePrincipal"}`(= backend identity)로
   정상 인증됨.

로그인 다음 스텝인 `az storage blob download`는 `ERROR: The specified blob does not exist`
(`ErrorCode: BlobNotFound`)로 끝났는데, 이건 **정상/예상된 결과**다 — `MODEL_VERSION` ConfigMap이 아직
placeholder 값이라 ml 레포가 실제 모델을 안 올린 경로를 가리키고 있을 뿐, 인증/권한 문제가 전혀 아니라는
게 이걸로 확정됐다.

**오늘 세션에서 발견한 인프라 버그가 이걸로 전부 마무리됐다.** ACR 접미사 누락(`053b18d`) → Key Vault
시크릿 재현성(`fdc0d1b`) → Workload Identity 로그인 방식(`15572fe` → `971ec6e`) 순으로 하나씩 잡았고,

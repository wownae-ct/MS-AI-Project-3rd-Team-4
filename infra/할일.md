## P1 — 실제 IaC 배포 절차

리소스그룹은 Bicep 스코프 밖이라 최초 1회 수동 생성 필요. 그 다음부터는 `scripts/deploy-infra.sh`
하나로 반복 가능.

```bash
# 1) 리소스그룹 생성 (최초 1회만)
az group create --name project-3rd-team-4 --location koreacentral # 이미 있음

# 2) 원샷 배포 스크립트 (문법검증 -> what-if 미리보기 -> 확인 후 실배포)
./scripts/deploy-infra.sh
# --yes 옵션 주면 what-if 확인 프롬프트 없이 바로 배포(비추천, 처음엔 반드시 what-if부터 눈으로 볼 것)
```

**배포 실패 가능 지점(사전에 알아둘 것):**

- Azure OpenAI `chat`/`chat-mini`(gpt-5.4, gpt-5.4-mini) capacity 250이 구독 쿼터를 초과할 수 있음 —
  실패하면 `infra/bicep/modules/openai.bicep`의 `chatDeploymentCapacity` 낮춰서 재시도.
- `postgresAdminLogin`/`Password`가 `.env`에서 안 읽히면 `pgadmin`/`CHANGE_ME_LOCAL_ONLY`로 폴백되는데,
  이 상태로 배포되면 나중에 알아채기 어려우니 `what-if` 출력에서 관리자 계정 이름이 `team4admin`으로
  나오는지 확인.

**배포 성공 후 출력값 받아두기** (다음 단계에서 다 필요함):

```bash
az deployment group show --resource-group project-3rd-team-4 --name main --query properties.outputs
```

`aksName`, `oidcIssuerUrl`, `backendIdentityClientId`, `acrLoginServer`, `keyVaultUri`, `postgresFqdn`,

### Azure AD 앱 등록 + Federated Identity Credential (OIDC, 장기 키 없이 GitHub Actions 인증)

```bash
# 앱 등록
az ad app create --display-name "project-3rd-team-4-github-oidc"
# 위에서 나온 appId를 아래에 사용
az ad sp create --id <appId>

# federated credential — backend 브랜치 push용
az ad app federated-credential create --id <appId> --parameters '{
  "name": "github-backend-branch",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:<org>/<repo>:ref:refs/heads/backend",
  "audiences": ["api://AzureADTokenExchange"]
}'
# infra-deploy.yml, frontend-ci.yml 등 다른 트리거(PR, frontend 브랜치)에도 필요하면 subject만 바꿔서 반복

# 구독에 Contributor 역할 부여 (또는 리소스그룹 스코프로 최소화)
az role assignment create --assignee <appId> --role Contributor \
  --scope /subscriptions/<subId>/resourceGroups/project-3rd-team-4
```

## P3 — Ingress / 도메인 / TLS (결정 완료, 2026-08-13)

- [x] **도메인**: AKS/Azure LoadBalancer 자동생성 DNS 라벨로 확정(실도메인 구매 X). production만 라벨을
      받고(`aicoach-production.koreacentral.cloudapp.azure.com`), staging은 **같은 컨트롤러의 같은 공인
      IP를 `nip.io`로 재사용**(`<IP를-하이픈으로-치환>.nip.io`) — `frontend-ci.yml`이 PR 프리뷰/프로덕션
      둘 다 `VITE_API_BASE` 시크릿 하나만 쓰는 걸 보면 브라우저가 staging 백엔드를 직접 호출하는 경로가
      없어서, staging까지 예쁜 도메인/별도 컨트롤러가 필요 없다고 판단(2026-08-13, nginx 2벌 → 1벌로
      재정리). DNS 이름 레이블 범위는 ACR과 동일하게 "재사용 안 함(No Reuse)". 상세 근거는
      [k8s/ingress-nginx/README.md](k8s/ingress-nginx/README.md) 참고.
- [x] **TLS**: cert-manager + Let's Encrypt 운영 ACME 자동 발급으로 확정(HTTP만 X, `nip.io`도 실제
      공인 DNS라 HTTP-01 challenge 그대로 통과). ClusterIssuer는 컨트롤러가 1개라 **`letsencrypt-nginx`
      1개만** 있으면 됨. 상세는 [k8s/cert-manager/README.md](k8s/cert-manager/README.md) 참고.
- [x] `infra/k8s/overlays/backend-production/ingress.yaml` — 호스트/`ingressClassName: nginx`/`tls`/
      cert-manager 어노테이션 확정 완료.
- [x] `infra/k8s/overlays/backend-staging/ingress.yaml` — 구조는 완료했지만 호스트값은 ingress-nginx의
      공인 IP가 나와야 알 수 있어서 `<STAGING_NIP_IO_HOST_TBD>` 자리표시자로 남겨둠(P1 이후 채울 항목,
      아래 실행 단계 1번 참고).

**남은 실행 단계 (AKS 클러스터 배포 = P1 이후, 순서대로):**

1. `infra/k8s/ingress-nginx/README.md`대로 Helm 설치 1회 →
   `kubectl get svc -n ingress-nginx ingress-nginx-controller`로 공인 IP 확인 →
   `infra/k8s/overlays/backend-staging/ingress.yaml`의 `<STAGING_NIP_IO_HOST_TBD>`를
   `<IP를-하이픈으로-치환>.nip.io`로 채우기 → `nslookup aicoach-production.koreacentral.cloudapp.azure.com`
   으로 DNS 라벨 반영 확인(**미검증**)
2. `infra/k8s/cert-manager/README.md`대로 cert-manager Helm 설치
3. `cluster-issuer.yaml`의 `<LETSENCRYPT_EMAIL>`을 실제 팀 이메일로 교체 후 `kubectl apply`
4. ArgoCD가 backend Application을 sync하면 Ingress가 생성되고 cert-manager가 자동으로 인증서 발급
   시도 — `kubectl get certificate -n staging`/`-n production`으로 `READY: True` 확인(**미검증**)

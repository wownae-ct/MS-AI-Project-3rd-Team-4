# 인프라 실배포 트러블슈팅 기록 (2026-08-13, 첫 실배포)

> `구현-요약.md`가 "왜 이렇게 설계했나"라면, 이 문서는 **실제로 `az deployment group create` 돌리면서
> 만난 에러와 고친 방법**만 모은 것. 다음에 리소스그룹 새로 파거나 다른 프로젝트에 이 Bicep을 재사용할 때
> 같은 삽질 반복 안 하려고 정리.

## 요약: 만난 에러 8개

| # | 에러 | 원인 | 고친 파일 |
|---|---|---|---|
| 1 | `RegistryNameAlreadyInUse` (aicoachacr) | ACR 이름은 Azure 전체에서 유일해야 함 — 흔한 이름이라 충돌 | 코드 문제 아님, `NAME_PREFIX` 바꿔서 해결 |
| 2 | `ConcurrentFederatedIdentityCredentialsWritesForSingleManagedIdentity` | 같은 Managed Identity 밑에 Federated Credential 2개(staging/production)를 반복문으로 만들면 Bicep이 기본 병렬 배포 → Azure API가 동시 쓰기 자체를 거부 | `aks.bicep` |
| 3 | `"enablePurgeProtection" cannot be set to false` | 이름 충돌 재시도 과정에서 soft-delete된 Key Vault가 purge protection true인 채로 남음 — false로 덮어쓰려다 충돌(불가역 속성) | `keyvault.bicep` |
| 4 | `SKU 'Standard' for model 'text-embedding-3-small' not supported in koreacentral` | embedding 배포만 `Standard` SKU로 하드코딩, chat/chat-mini는 이미 `GlobalStandard` | `openai.bicep` |
| 5 | `AadAuthOperationCannotBePerformedWhenServerIsNotAccessible` (1차) | Postgres 서버가 ARM상 Succeeded 직후에도 AAD 서브시스템은 준비 안 됨 | `postgres.bicep` (`@retryOn` 추가 — 부분적 해결) |
| 6 | 같은 에러 재발 | `properties.network.publicNetworkAccess`를 명시 안 하면 최신 API 버전 기본값이 `Disabled`로 나옴 | `postgres.bicep` (`network.publicNetworkAccess: 'Enabled'` 추가 — 근본 원인 아니었음) |
| 7 | 같은 에러 3번째 재발 | Azure의 알려진 미해결 이슈([azure-postgresql#127](https://github.com/Azure/azure-postgresql/issues/127)) — `dependsOn`이 만족돼도 AAD 작업 준비 여부는 별개 타이밍 | `postgres.bicep` — 네이티브 `administrators` 리소스를 **재시도 스크립트**(`deploymentScripts`, 실패 시 30초 간격 최대 20회)로 완전히 교체 |
| 8 | (버그 아님) Windows `cp949` 콘솔에서 `az` CLI가 Bicep의 em-dash(`—`) 포함 문자열 출력하려다 `UnicodeEncodeError` | 로케일 인코딩 문제 | `scripts/deploy-infra.sh` (`export PYTHONIOENCODING=utf-8`) |

## 상세

### 1. ACR 이름 전역 충돌
ACR/Storage/Key Vault/Static Web App 이름은 전부 **Azure 전체에서 유일**해야 함(구독/리소스그룹 스코프 아님).
`aicoach`처럼 흔한 단어 조합은 다른 누군가 이미 쓰고 있을 가능성이 높음. 이게 계기가 돼서 `NAME_PREFIX`를
하드코딩에서 `infra/.env` + 대화형 입력으로 바꾸는 리팩토링을 하게 됨(7번 항목).

### 2. AKS Federated Identity Credentials 동시 쓰기
```bicep
resource federatedCredentials '...' = [for ns in backendNamespaces: { ... }]
```
Bicep 반복문은 기본적으로 **병렬** 배포. 근데 같은 Managed Identity에 Federated Credential을 동시에 여러 개
쓰는 건 Azure API가 지원 안 함. 고침: `@batchSize(1)` 데코레이터로 순차 배포 강제.

### 3~4. Key Vault purge protection / Foundry embedding SKU
표 참고. 둘 다 한 줄 수정으로 끝난 명확한 버그.

### 5~7. Postgres AAD 관리자 등록 — 3번 시도 끝에 근본 해결
**1차 시도(`@retryOn`)**: ARM이 특정 에러 코드를 만나면 자동 재시도하는 데코레이터. 이론상 맞는 접근이었지만
재발함 — 재시도 횟수/백오프가 이 특정 지연에는 부족했던 것으로 추정.

**2차 시도(`publicNetworkAccess: 'Enabled'`)**: what-if에서 라이브 리소스가 `Disabled`로 나온 걸 보고 이게
원인이라 판단해서 고침. 컴파일은 통과했지만 **같은 에러가 또 재발** — 진짜 원인이 아니었음(사용자가
"편한 방법으로만 해결하려 하지 말라"고 정확히 지적함).

**3차 시도(최종, 근본 해결)**: GitHub에 정확히 같은 이슈가 이미 보고돼 있었고([azure-postgresql#127](https://github.com/Azure/azure-postgresql/issues/127)),
Microsoft도 확정된 해결책을 안 내놓은 **알려진 서비스 버그**라는 걸 확인. `dependsOn`이 만족돼도 서버가
"AAD 작업을 받을 준비가 됐는지"는 별개 타이밍이라 Bicep 리소스 선언만으로는 100% 신뢰 가능한 방법이 없음.
그래서 네이티브 `Microsoft.DBforPostgreSQL/flexibleServers/administrators` 리소스를 지우고,
`Microsoft.Resources/deploymentScripts`로 **실제 `az postgres flexible-server ad-admin create` 명령을
직접 반복 시도**(실패 시 30초 간격, 최대 20회=10분)하는 스크립트로 교체. "얼마나 기다려야 하는지 추측"이
아니라 "실제로 될 때까지 확인"하는 방식이라 근본적으로 다름 — 스크립트가 진짜 Azure API를 호출해야 해서
전용 Managed Identity(이 Postgres 리소스에만 국한된 Contributor 권한)를 하나 추가함.

### 8. Windows 콘솔 인코딩
`az bicep build --stdout`처럼 콘솔에 직접 출력하는 명령이, Bicep 파일의 한글 주석에 섞인 em-dash(`—`) 같은
유니코드 문자를 cp949(한글 Windows 기본 코드페이지)로 못 그려서 크래시. `PYTHONIOENCODING=utf-8`을
스크립트 시작부에 export해서 해결. `--outfile`로 파일 출력할 때는 원래도 문제 없었음(콘솔에 안 찍으니까).

## 그 외 이번 세션에 같이 정리한 것 (버그 아님, 요청 반영)

- **`NAME_PREFIX` 하드코딩 완전 제거**: `main.bicep`(기본값 없앰) + `dev.bicepparam`(`readEnvironmentVariable`
  2번째 인자 없이 — 값 없으면 즉시 빌드 에러) + `scripts/deploy-infra.sh`(대화형 프롬프트, 3~12자 영문
  소문자+숫자 검증). 이유: 팀/프로젝트 바뀔 때마다 코드를 안 고쳐도 재사용 가능하게.
- **`clusterAdminPrincipalIds` 파라미터 위치 정리** — 모듈 사이에 끼어있던 걸 다른 파라미터들과 함께 파일
  상단으로 이동(`main.bicep` 리팩토링).
- **`storage.bicep`의 중복 `@minLength(3)` 제거** — `main.bicep`에 이미 중앙화된 제약을 8개 모듈 중
  이 파일만 로컬로 재검증하고 있던 걸 통일.

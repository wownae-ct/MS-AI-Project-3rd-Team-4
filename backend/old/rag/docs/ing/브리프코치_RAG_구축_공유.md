# 브리프코치 RAG 구축 결과 공유

## 1. RAG가 뭐고, 왜 필요한가요?

RAG(Retrieval-Augmented Generation)는 쉽게 말해 "AI가 답을 지어내지 않고, 미리 준비한 진짜 자료에서 관련 내용을 찾아서 그걸 근거로 답하게 하는 방식"이에요.

브리프코치에는 사용자가 답변을 하면 코칭 코멘트를 주는 AI 에이전트(coach)와, 그 코멘트가 "진짜로 근거 있는 말인지" 검증하는 AI 에이전트(verify, 근거검증)가 있어요. 예를 들어 coach가 "이 답변은 두괄식으로 시작 안 해서 아쉬워요"라고 말했다면, verify는 "두괄식이 왜 중요한지"에 대한 진짜 화법 가이드 문서를 찾아서 그 코멘트가 근거 있는지 확인해야 해요.

그러려면 먼저 화법 가이드 문서들을 **AI가 검색할 수 있는 형태**로 만들어둬야 하는데, 그 작업이 이번에 한 RAG 구축이에요. (coach/verify 에이전트 자체는 아직 안 만들었고, 이번엔 "검색 기능"만 완성했어요.)

## 2. 데이터셋 — 뭐가 몇 개 들어갔나요?

정확히 **40건**의 화법/커뮤니케이션 가이드 문서가 들어갔어요. (`data/rag_corpus/speech_guide_corpus.json`)

카테고리별로 나눠보면:

| 카테고리 | 건수 |
| --- | --- |
| STAR 관련 (STAR / STAR 정의 / STAR 예시) | 6건 |
| 두괄식 관련 (두괄식 / 두괄식 정의 / 두괄식 예시) | 3건 |
| 팀 기술리뷰 | 3건 |
| 고객 설명 | 3건 |
| 기술 설득 | 3건 |
| 전달력 | 2건 |
| 의사소통 저해요인 | 2건 |
| 장애·설명 공통 | 2건 |
| 그 외 (간결성/시간관리/꼬리질문/문서작성 관련 등 개별 주제) | 14건 |
| **합계** | **40건** |

내용 예시를 몇 개 보여드리면:
- "두괄식 화법이 필요한 이유"
- "STAR 기법이란 무엇인가"
- "코드가 아니라 나를 주어로 말하기 (I-message)" — 팀 기술리뷰 카테고리
- "장애 보고는 발견→영향→조치 순서로" — 장애·설명 공통 카테고리

출처는 국립국어원 『한눈에 알아보는 공공언어 바로 쓰기』, NCS(국가직무능력표준) 의사소통능력 학습모듈 같은 공공저작물을 팀이 직접 읽고 재구성한 것과, 팀이 직접 작성한 콘텐츠가 섞여 있어요. 원문을 그대로 베낀 게 아니라 팀이 다시 쓴 거라 저작권 문제 없어요.

## 3. 어떻게 검색하나요? (쉬운 비유로)

1. **잘게 쪼개기 (청킹)**: 문서 하나를 통째로 검색하면 관련 없는 내용까지 딸려 나와요. 그래서 문서를 300~500자 단위로 잘게 쪼개요. 문장 중간에서 뚝 끊기지 않게, 문단·문장 단위로 자연스럽게 나눠요.

2. **숫자로 바꾸기 (임베딩)**: 각 조각을 "의미를 숫자로 표현한 벡터"로 바꿔요(Azure OpenAI의 `text-embedding-3-small` 모델 사용). 비유하자면, "두괄식"이라는 말과 "결론부터 말하기"라는 말은 표현은 다르지만 뜻이 비슷하니까 숫자로 바꿨을 때도 서로 가까운 위치에 놓이게 돼요.

3. **질문도 숫자로, 그리고 제일 가까운 걸 찾기**: 사용자 질문("두괄식이 뭐야?" 같은)도 똑같이 숫자로 바꾼 다음, 저장해둔 문서 조각들 중에서 "숫자상 제일 가까운" 것부터 찾아와요. 이 검색을 빠르게 해주는 게 Postgres 데이터베이스의 `pgvector`라는 기능이에요.

실제로 해본 검색 예시 5개예요 (전부 원하는 결과가 1등으로 나왔어요):

| 질문 | 찾아온 결과 |
| --- | --- |
| "두괄식이 뭐야" | "두괄식 화법이 필요한 이유" (두괄식) |
| "STAR 기법 예시 보여줘" | "개발자 상황의 STAR 답변 예시" (STAR 예시) |
| "코드 리뷰할 때 어떻게 말해야 해" | "코드가 아니라 나를 주어로 말하기" (팀 기술리뷰) |
| "필러워드 줄이는 법" | "필러워드와 침묵의 관계" (전달력) |
| "고객한테 기술적 제약 설명하는 법" | "무엇을 원하는지부터 확인하기" (고객 설명) |

## 4. 어떤 테스트를 했고, 다 통과했나요?

**자동 테스트 32개** — 문장이 안 끊기고 잘리는지, 검색 결과 순서가 안 뒤섞이는지, 데이터베이스에 저장할 때 오류 없이 안전하게 처리되는지 같은 걸 코드로 자동 검증하는 테스트예요. 전부 통과했어요.

**진짜 서버(Azure Postgres, Azure OpenAI)에 직접 연결해서 검증**: 로컬 테스트만으로는 부족해서, 실제로 우리 팀 Azure 계정에 연결해서 확인했어요.
- 데이터베이스에 실제로 스키마(테이블 구조)를 만들고
- 색인 스크립트(문서를 쪼개서 검색 가능하게 만드는 작업)를 두 번 연속 실행해봐서, 다시 돌려도 데이터가 꼬이지 않는지(idempotent, "여러 번 돌려도 결과가 같음") 확인하고
- 위 5개 검색 예시가 실제로 다 정확하게 나오는지 확인했어요.

**실제 클러스터의 자동 실행 작업까지 확인**: 매일 새벽 3시에 자동으로 문서를 다시 색인하는 작업(`rag-reindex`)이 있는데, 이걸 수동으로 강제 실행해서 실제로 성공하는지까지 확인했어요(`indexed 40 docs, 40 chunks`로 성공). 이 과정에서 배포 설정에 진짜 버그 2개(Key Vault라는 곳에 비밀정보가 안 올라가 있던 것, 인증 관련 설정 라벨이 하나 빠져 있던 것)를 발견해서 같이 고쳤어요 — 코드만 맞다고 끝난 게 아니라, 실제로 돌아가는 것까지 확인한 거예요.

## 5. 지금 어디까지 됐고, 다음은 뭔가요?

**RAG 검색 기능 자체는 완성 + 검증까지 끝났어요.** "질문을 던지면 관련 문서를 찾아준다"는 기능은 실제 서버에서 확인 완료.

**다음 단계**: coach(코칭) 에이전트와 verify(근거검증) 에이전트가 이 검색 기능을 실제로 가져다 쓰는 것 — 그건 아직 안 만들었고 다음 작업이에요.

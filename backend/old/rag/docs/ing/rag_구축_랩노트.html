01

RAG가 뭔지 — 개념부터

Retrieval-Augmented Generation · "찾아서, 그걸 근거로 답하기"

LLM(대형 언어모델)은 방대한 텍스트를 학습해서 그럴듯한 문장을 만들어내는 데는 뛰어나지만, 가끔 "모르는 걸 아는 척 지어내는" 문제가 있다. 이걸 흔히 할루시네이션이라고 부른다. 예를 들어 "이 답변은 STAR 구조를 잘 지켰다"라고 LLM이 말했을 때, 그게 실제로 어떤 기준에 근거한 판단인지, 아니면 그냥 그럴듯하게 지어낸 말인지 우리는 알 방법이 없다.

개념

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 이 문제를 줄이는 방법이다. LLM이 답을 혼자 지어내게 두는 대신, 먼저 믿을 수 있는 문서 더미에서 관련 내용을 찾아온 다음, 그 내용을 근거로 삼아 답하게 만든다. 시험 볼 때 "책 보고 풀어도 됩니다"라고 하면 답의 신뢰도가 확 올라가는 것과 비슷하다 — LLM에게도 참고할 "책"을 손에 쥐여주는 것이다.

브리프코치에서는 이 "책"이 STAR 기법·두괄식 화법·기술 커뮤니케이션 같은 화법 가이드 문서 40건이다. 나중에 근거검증(guardrail) 에이전트가 코칭 코멘트("이 답변은 두괄식이 아니에요" 같은)를 만들 때, "그 판단이 진짜 이 가이드 문서 중 어딘가에 근거하고 있는지"를 확인하는 데 이 RAG 시스템을 쓴다. 오늘 만든 건 정확히 그 "책"을 만들고, 빠르게 찾아볼 수 있게 색인을 붙이는 작업이다. coach/verify 에이전트가 실제로 이 책을 펼쳐보는 것은 다음 단계 작업이다.

02

코퍼스 — 무엇을 모았나

data/rag_corpus/speech_guide_corpus.json

코퍼스(corpus)는 "찾아볼 대상이 되는 원본 문서 뭉치"를 부르는 말이다. 브리프코치의 코퍼스는 정확히 40건의 짧은 화법 가이드 글로 구성돼 있고, 각 글은 doc_number(고유 번호), category(카테고리), title, source(출처), body_text(본문) 다섯 개 필드를 가진 JSON 객체 하나다.

카테고리 분포

카테고리 묶음건수
STAR (기법·정의·예시)6
기술 설득 / 고객 설명 / 팀 기술리뷰9
두괄식 (화법·정의·예시)3
전달력 / 의사소통 저해요인 / 장애·설명 공통6
그 외 개별 주제 (간결성·시간관리·꼬리질문·문서작성 등 14종)14
합계40

번호가 16, 17, 28에서 비는 이유

doc_number를 쭉 나열해보면 16·17·28이 빠져있다. 실수로 빠진 게 아니라 의도적인 정리 결과다. 16·17번은 원래 두괄식/공공언어 원칙을 다뤘는데, 나중에 더 정확한 1차 자료(국립국어원 공식 간행물)를 직접 확인해보니 처음 정리했던 내용이 부정확했다는 게 드러나서 제외했다. 28번은 애초에 코퍼스 항목이 아니라 작업 중 남긴 메타노트였다. 대신 상대적으로 얇았던 기술 설득과 장애·설명 공통 카테고리를 각각 한 건씩 새로 써서 42번, 43번으로 보강해 정확히 40건을 맞췄다.

저작권은 어떻게 다뤘나

상업 사이트 글을 그대로 긁어오지 않았다. 국립국어원 『한눈에 알아보는 공공언어 바로 쓰기』, NCS 의사소통능력 학습모듈 같은 공공저작물을 팀이 직접 읽고 재구성했고, 나머지 상당수는 팀이 직접 쓴 원본 콘텐츠다(예: "코드가 아니라 나를 주어로 말하기(I-message)", "장애 보고는 발견→영향→조치 순서로"). 그래서 출처(source 필드) 없이 null인 문서도 많은데, 이건 "팀 자체 작성"이라는 뜻이지 출처를 빠뜨린 게 아니다.

03

청킹 — 문서를 왜 잘게 쪼개나

backend/rag/index/chunker.py

문서 한 편을 통째로 검색 대상으로 삼으면 문제가 생긴다. 문서가 길면 그 안에 관련 없는 내용까지 잔뜩 딸려 들어오고, 반대로 너무 잘게 쪼개면 문장이 맥락을 잃는다. 그래서 300~500자 정도 되는 "청크(chunk)" 단위로 나눠서 저장한다 — 딱 한 문단 분량, 검색했을 때 "이 부분이 정확히 관련 있다"고 말할 수 있을 만큼 좁으면서도 문장이 끊기지 않을 만큼은 넉넉한 크기다.

알고리즘

문단 단위로 먼저 순서대로 이어 붙이다가, 다음 문단을 더하면 500자를 넘을 것 같으면 거기서 끊고 새 청크를 시작한다("그리디 패킹"). 그런데 문단 하나가 그 자체로 500자를 넘는 경우도 있다 — 이때만 예외적으로 그 문단 안에서 문장 단위로 같은 방식을 적용한다. 어떤 경우에도 문장 중간에서는 절대 자르지 않는다. 크기 제한보다 "뜻이 안 깨지는 것"이 항상 우선이다.

코퍼스 40건 대부분은 원래부터 한 문단, 300~500자 정도로 써져 있어서 대부분 청크 1개로 끝난다. 문단이 길어서 청크가 2개 이상 나뉘는 문서만 소수 있다.

04

임베딩 — 텍스트를 숫자로 바꾸기

backend/app/core/embeddings.py · Azure OpenAI text-embedding-3-small

벡터란

임베딩(embedding)은 문장을 숫자로 이뤄진 좌표(벡터)로 바꾸는 작업이다. "의미가 비슷한 문장은 좌표도 가깝게" 배치되도록 학습된 모델이 이 변환을 해준다. 예를 들어 "결론부터 말하기"와 "두괄식"은 글자는 완전히 다르지만 뜻이 비슷하니 벡터 공간에서도 가까운 자리에 놓인다. 이 프로젝트는 Azure OpenAI의 text-embedding-3-small 모델을 써서 문장 하나를 1536개의 숫자로 이뤄진 벡터로 바꾼다.

청크 40여 개를 하나하나 API로 보내면 느리고 비효율적이라, 16개씩 묶어서(배치) 한 번에 임베딩 요청을 보낸다.

코드 리뷰에서 잡힌 버그

배치로 응답을 받을 때, API가 보낸 순서 그대로 결과를 돌려준다고 그냥 믿으면 위험하다. 응답에 딸려오는 item.index 필드가 바로 "이 결과가 원래 몇 번째 입력이었는지"를 알려주는 용도인데, 처음엔 이 필드를 안 쓰고 리스트 순서만 믿었다. 리뷰에서 "응답 순서를 실제로 뒤섞어서 반환하는 가짜 테스트를 만들어야, 이 재정렬 로직이 진짜 있는지 검증할 수 있다"는 지적을 받고 item.index로 명시적으로 재정렬하도록 고쳤다.

05

pgvector — DB가 "비슷한 것"을 찾는 법

PostgreSQL + pgvector 확장 · HNSW 인덱스 · cosine distance

개념

pgvector는 일반 PostgreSQL에 "벡터를 저장하고, 벡터끼리 얼마나 가까운지 빠르게 계산하는" 기능을 얹어주는 확장이다. 벡터가 40개뿐이면 하나하나 다 비교해도 되지만, 실제 서비스에서는 수만~수백만 개가 될 수 있어서 HNSW 라는 인덱스 구조를 쓴다 — "완벽하게 가장 가까운 것"을 찾는 대신 "충분히 가까운 것"을 훨씬 빠르게 찾아주는 근사 탐색 방식이라고 생각하면 된다.

"얼마나 가까운지"는 코사인 거리(cosine distance)로 잰다. 값이 작을수록 더 비슷하다는 뜻이다(0에 가까울수록 거의 같은 의미). 아래는 실제로 이 프로젝트의 검색 함수를 다섯 개 질문으로 돌려본 결과다 — 거리 숫자가 작은 순서대로 정렬돼 나온다.

다섯 질문 전부 카테고리·제목이 질문 의도와 정확히 맞아떨어졌다 — 코퍼스·청킹·임베딩·검색 경로 전체가 실제로 의미를 이해하고 찾아온다는 뜻이다.

06

재조립 — 가장 실수하기 쉬웠던 부분

backend/rag/index/assemble.py

임베딩 API를 호출할 때 40개 문서의 청크를 한 줄로 쭉 펴서 한 번에 보내는 게 훨씬 효율적이다. 문제는 그 다음이다 — 평탄화된 임베딩 리스트를 다시 "몇 번째 문서의 몇 번째 청크"였는지 정확히 되돌려 붙여야 한다. 

# 문서마다 청크 개수가 다르므로(1개짜리, 3개짜리...) 오프셋을 누적해서 추적
offset = 0
for doc, chunk_texts in chunked:
    doc_embeddings = embeddings[offset : offset + len(chunk_texts)]
    offset += len(chunk_texts)
    # ... 이 doc_embeddings를 doc에 붙여서 InsertableDoc으로 만듦
왜 위험한가

이 오프셋 계산이 하나라도 틀리면 A 문서의 청크에 B 문서의 임베딩이 붙는다. 그런데 이건 에러를 던지지 않는다 — 그냥 벡터 값이 하나 잘못 들어갈 뿐이라, 프로그램은 멀쩡히 끝나고 검색 결과만 "미묘하게" 이상해진다. 가장 알아채기 어려운 유형의 버그다. 그래서 이 재조립 로직만 따로 떼서, 청크 수가 다른 문서 여러 개를 섞어 넣고 "각 청크가 진짜 자기 임베딩과 정확히 짝지어지는지"를 확인하는 전용 테스트를 만들었다. 그리고 마지막에 offset != len(embeddings)이면 조용히 넘어가지 않고 바로 예외를 던지게 했다(디버깅용 assert가 아니라 진짜 ValueError로 — assert는 파이썬을 최적화 모드로 실행하면 통째로 사라져 버리기 때문).

07

DB에 저장하기 — 왜 TRUNCATE 대신 upsert인가

backend/app/db/queries/speech_guide.py

rag-reindex는 매일 새벽 3시에 자동으로 다시 돈다. 처음 든 생각은 "매번 그냥 싹 지우고 새로 넣으면 되지 않나"였다. 그런데 그러면 문제가 생긴다 — speech_guide_chunk의 id는 데이터베이스가 자동으로 매기는 번호라서, 싹 지우고 다시 넣으면 재색인할 때마다 같은 내용인데도 id가 바뀐다. 나중에 근거검증 에이전트가 "이 코칭 코멘트는 청크 id 123을 근거로 삼았다"처럼 기록해두면, 다음날 재색인 후엔 그 id가 사라져 있는 문제가 생긴다.

해결책 — 자연키

그래서 코퍼스의 doc_number와 (doc_id, chunk_index) 조합을 "자연키"로 삼았다. 내용이 안 바뀐 문서·청크는 재색인해도 같은 id를 그대로 유지한다 — SQL의 INSERT ... ON CONFLICT (...) DO UPDATE 구문으로, "이미 있으면 업데이트, 없으면 새로 삽입"을 한 문장으로 처리한다.

외래키(FK) 순서 문제

코퍼스에서 아예 빠진 문서(이번 세션의 16·17·28번 같은)는 DB에서도 지워야 한다. 그런데 speech_guide_chunk는 speech_guide_doc을 참조하고 있고 (외래키), 이 참조에 "부모가 지워지면 자식도 자동으로 같이 지운다"는 설정 (ON DELETE CASCADE)이 없다. 그래서 자식 청크가 남아있는 채로 부모 문서부터 지우려고 하면 데이터베이스가 참조 무결성 위반으로 막는다. 그래서 코드에서 자식(청크)을 먼저 지우고, 그다음 부모(문서)를 지우도록 순서를 명시적으로 맞췄다.

08

검색 함수 — 질문 하나가 던져지면

backend/app/agents/retriever/search.py · search_speech_guide(query, k)

실제 질문이 들어왔을 때 벌어지는 일은 세 단계뿐이다.

async def search_speech_guide(query, k):
    # 1) 질문 문장도 코퍼스와 똑같은 방식으로 벡터로 바꾼다
    query_embedding = await embed_query(client, query, ...)
    # 2) DB에서 코사인 거리가 가장 가까운 k개 청크를 가져온다
    rows = await search_chunks_by_embedding(conn, query_embedding, k)
    # 3) 결과를 다루기 쉬운 형태(SpeechGuideMatch)로 감싸서 반환
    return [SpeechGuideMatch(**dict(r)) for r in rows]

"질문도 결국 코퍼스랑 똑같은 방법(임베딩)으로 벡터로 바꿔서, 같은 공간에서 거리를 재는 것"이라는 게 핵심이다 — 그래야 "의미가 비슷한 것끼리 가깝다"는 임베딩의 성질을 검색에 그대로 활용할 수 있다.

09

인증 — API 키 없이 접속하기

Azure AD (Entra ID) · Managed Identity · Workload Identity

왜 API 키를 안 쓰나

보통은 비밀번호나 API 키를 코드/설정 파일에 넣어서 인증한다. 근데 그런 값은 어딘가로 새어나갈 위험이 항상 있다(오늘 세션에서도 실제로 관련 사고가 하나 있었을 정도다). 그래서 이 프로젝트는 Postgres도, Azure OpenAI도 고정된 비밀값을 아예 안 쓴다.

대신 Managed Identity라는 걸 쓴다 — Azure가 "이 애플리케이션이 진짜 우리가 등록해준 그 앱이 맞다"는 걸 매번 새로 확인해서 짧은 시간만 유효한 토큰을 발급해주는 방식이다. 신분증을 코드에 박아두는 대신, 필요할 때마다 창구에 가서 새 신분증을 받아오는 것과 비슷하다. 클러스터 안에서는 이걸 Workload Identity라는 메커니즘으로 연결한다.

로컬 개발 환경(Postgres가 클러스터 밖에 없는)과 실제 클러스터, 두 가지를 하나의 설정으로 지원하기 위해 database_auth_mode라는 값을 뒀다 — 로컬은 "password"(연결 문자열에 비밀번호 포함), 클러스터는 "aad" (비밀번호 없는 연결 문자열 + 연결 시점에 AAD 토큰을 따로 전달)로 명확히 분기시켰다.

자동 테스트가 전부 초록불이어도, 그건 "코드가 논리적으로 맞다"는 것만 증명한다. 실제로 진짜 Postgres·Azure OpenAI에 붙여서 확인해보니, 0001_init.sql 스키마가 이 프로젝트에서 한 번도 적용된 적이 없었다는 사실부터 드러났다. 마이그레이션을 실제로 적용하고, rag.index를 두 번 실행해서 청크 id가 안 바뀌는지(진짜 idempotent인지) 확인하고, 위 5개 검색 쿼리로 실제 정확도를 확인했다.

실제 클러스터에서 터진 진짜 버그 2개

로컬 검증도 끝났으니 다 됐다고 생각했지만, 실제 Kubernetes 클러스터의 자동 색인 작업 (rag-reindex CronJob)을 수동으로 트리거해보니 또 다른 층위의 문제가 나왔다 — 코드 리뷰로는 절대 못 잡는 종류다.

  1. Key Vault 시크릿 미배포 — pg-connstr 비밀정보가 Bicep(인프라 코드) 파일 안에는 있었지만, 실제로 Azure에 배포된 적이 없었다. 코드는 맞는데 실제 인프라 상태가 그 코드를 반영하지 않고 있었던 것.
  2. 인증 라벨 누락 — rag-reindex 파드 설정에 azure.workload.identity/use: "true" 라벨이 처음부터 빠져 있었다. 이 라벨이 없으면 앞서 §9에서 설명한 Workload Identity 메커니즘 자체가 작동을 안 해서, 인증 시도가 전부 실패한다. python -m rag.index가 이제껏 늘 NotImplementedError로 먼저 죽어서 인증 단계까지 간 적이 없었기 때문에 아무도 눈치채지 못하고 있었던 기존 버그였다.
최종 확인

두 버그를 고치고 다시 트리거하니 indexed 40 docs, 40 chunks로 실제 클러스터에서 정상 완료됐다. 이걸로 코퍼스 → 청킹 → 임베딩 → 색인 → 검색 → 실제 배포까지 전 구간이 실제 환경에서 검증됐다.

11

오늘의 교훈

다음에 비슷한 파이프라인을 만들 때 그대로 다시 써먹을 만한 것들.

  • "코드가 맞아 보인다"와 "실제로 동작한다"는 완전히 다른 문장이다. diff 리뷰와 자동 테스트는 논리적 정합성만 증명한다. 실제 인프라(진짜 DB, 진짜 인증, 진짜 클러스터)에 직접 붙여봐야만 드러나는 배포 상태 불일치가 있다 — 오늘의 두 버그 모두 코드는 처음부터 맞았고, "배포됐다고 가정한 것"이 틀렸던 경우다.
  • 테스트용 가짜 데이터는 "결과로 받고 싶은 형태"가 아니라 "실제로 시스템이 만들어내는 형태"를 기준으로 만들어야 한다. 검색 함수 테스트에서, 만약 dataclass 필드 목록을 기준으로 가짜 DB 응답(mock)을 만들었다면 실제 SQL이 반환하는 컬럼 하나가 빠져도 테스트가 통과해버렸을 것이다 — 실제 SELECT 쿼리를 기준으로 mock을 짜야 이런 "필드셋 드리프트" 버그를 잡을 수 있다.
  • 작아 보이는 순서·형식 실수가 조용히 큰 문제를 만든다. FK 삭제 순서 (자식 먼저), assert 대신 명시적 예외, 임베딩 배치 응답 재정렬 — 셋 다 "이 정도는 괜찮겠지" 싶을 만큼 작은 디테일이었지만, 방치하면 각각 트랜잭션 실패· 프로덕션에서 무력화되는 방어 코드·조용한 데이터 오염으로 이어질 수 있는 것들이었다.

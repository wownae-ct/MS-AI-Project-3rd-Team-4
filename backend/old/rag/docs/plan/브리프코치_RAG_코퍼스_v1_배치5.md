### DOC-29 [두괄식 정의] 표준국어대사전의 정의

출처: 국립국어원 표준국어대사전 — "두괄식" 표제어

표준국어대사전은 두괄식을 "글의 첫머리에 중심 내용이 오는 산문 구성 방식"으로 정의한다. 짝을 이루는 개념으로 중심 내용이 글 끝에 오는 미괄식, 처음과 끝에 반복 배치하는 양괄식이 있다. "두괄식으로 말하라"는 요구는 이 사전적 정의 그대로 — 결론에 해당하는 중심 문장을 답변의 맨 앞 문장으로 옮기라는 뜻이다.

### DOC-30 [STAR 정의] STAR 기법의 유래, 그리고 IT 업계에 각인된 계기

출처: 행동면접(behavioral interview) 기법 일반(톰 얀츠, 1982) + Amazon 공식 채용 페이지(aboutamazon.com)

STAR 기법은 상황(Situation)·과제(Task)·행동(Action)·결과(Result) 네 요소로 경험을 구조화해 답하는 방법이다. 학술적 기원은 1980년대 캐나다의 심리학자 톰 얀츠가 "과거 행동이 미래 행동을 가장 잘 예측한다"는 전제로 정립한 행동면접 기법이지만, IT 업계 지원자들에게 이 기법이 사실상 "필수 상식"으로 각인된 결정적 계기는 **Amazon(AWS 포함)**이다. Amazon은 자사 채용 공식 페이지에서 16가지 리더십 원칙(Leadership Principles)에 기반한 행동면접 질문에 "STAR 방식으로 답하라"고 명시적으로 안내하며, 전 세계 소프트웨어 엔지니어 채용의 상당 부분이 이 방식을 따르다 보니 개발자 커뮤니티에서는 "STAR = 톰 얀츠"보다 "STAR = 아마존 면접"으로 통하는 경우가 훨씬 많다. 코칭 멘트에서도 "이건 아마존 등 빅테크 면접에서 표준으로 쓰는 그 구조예요"라고 설명하는 편이 개발자 대상 청중에게 훨씬 와닿는다.

### DOC-31 [STAR 예시] 개발자 상황의 STAR 답변 예시 (원본 작성)

질문: "예상치 못한 장애를 해결한 경험을 말해주세요."

**나쁜 예시(구조 없음)**: "저는 문제 해결을 잘합니다. 예전에 서버 장애가 났을 때도 침착하게 대응해서 팀에서 인정받았습니다."

**좋은 예시(STAR)**: "(S) 배포 직후 결제 API 응답 시간이 급증했습니다. (T) 원인 파악과 서비스 정상화가 제 담당이었습니다. (A) 로그를 확인해 DB 커넥션 풀이 고갈된 걸 발견하고, 커넥션 풀 크기를 임시로 늘리는 동시에 직전 배포를 롤백할 준비를 했습니다. (R) 20분 만에 응답 시간이 정상화됐고, 이후 커넥션 풀 사용률에 알람을 추가해 같은 장애가 재발하지 않았습니다."

차이는 명확하다 — 나쁜 예시는 자기 진술("잘합니다")뿐이고, 좋은 예시는 각 단계가 구체적 사실로 채워져 있다.

### DOC-32 [두괄식 예시] 기술 설명에서의 두괄식 vs 미괄식 (원본 작성)

질문: "이 기능을 지금 배포해도 되나요?"

**미괄식(나쁜 예시)**: "어제 QA에서 몇 가지 이슈가 나왔는데 대부분 사소한 UI 버그였고, 핵심 로직 테스트는 다 통과했습니다. 성능 테스트도 기준치 안에 들어왔어서, 결론적으로 지금 배포해도 괜찮다고 봅니다."

**두괄식(좋은 예시)**: "네, 지금 배포해도 됩니다. 어제 QA에서 나온 이슈는 전부 사소한 UI 버그였고, 핵심 로직과 성능 테스트는 모두 기준을 통과했습니다."

같은 정보인데도 두괄식은 청자가 첫 문장만 듣고도 결론(배포 가능)을 알고, 나머지는 그 결론에 대한 확인 차원으로 듣게 된다. 미괄식은 결론을 듣기 전까지 청자가 판단을 유보해야 한다.
